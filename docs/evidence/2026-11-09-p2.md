# Finding: `proving-ground.p2`, what shape should the boolean pipeline take?

Code: `spikes/p2/`, branch `spike-p2`. Raw output is in `spikes/p2/results/`, the commands are in
`spikes/p2/results/COMMANDS.txt` and `spikes/p2/run/sweep.sh`, and `python3 -I spikes/p2/analyse.py` regenerates the tables
below from those files.

## Question

Built on a copy of S1's boolean, should the kernel's boolean be (a) pure phases, each a map over its items with a
deterministic merge in a stable order, or (b) one shared graph mutated by tasks under fine-grained locks? Speed-up at 1, 2, 4
and 6 threads, identical output at every count, time lost to contention, the code each needs, and what each can hand back
when one pair fails partway (L5).

## What was measured

**The base.** `spikes/p2/src/pipeline.rs` is a copy of `spikes/s1/src/boolean.rs` with its phases rewritten as maps. S1's
limits carry over: planes, cylinders, spheres and bicubic NURBS faces, no seams or poles, no coincident surfaces, ray parity
against every face with no spatial index, and S1's own near-tangent failures.

**Shape (a), pure phases.** Each phase reads the frozen output of the ones before it. Only the merge writes.

| Phase | Items of the map | Serial step |
|---|---|---|
| Prepare | faces (trim polygons) | none |
| 1 broad | faces of A against all boxes of B | flatten in face order |
| 2 pairs | distinct surface pairs, then distinct edge-against-face tests | plan the task lists; merge in candidate order |
| 3 edge split | edges; then candidate pairs, twice | ids given in edge order; vertex merge sweep; pinch vertices; seeds of free loops |
| 4 face split | faces | concatenate regions in face order |
| 5 classify | regions | none |
| 6 stitch | none: serial | all of it |

**Shape (b), the shared graph**, is `spikes/p2/src/shared.rs`. Phases 2 and 3 are fused into one task per candidate pair, which
mutates a shared graph as it runs: a mutex on each edge holding its sorted stops and its per-face hit cache; a vertex table
striped by position across 4,096 locks (Herlihy and Shavit, *The Art of Multiprocessor Programming*, 2008, section 13.2.2,
on lock striping); per-face piece lists; a shared arena of new edges; a memo of sections per surface pair. A vertex gets its
id on arrival.

**What was left out of (b).** Phases 1 and 4 to 6 are (a)'s, run on a snapshot frozen from the graph, so faces are not split in
place and regions, labels and stitching are not shared. There is no undo. The arena is one mutex, not per-thread bump
allocation. Nothing was done to canonicalise order. S1's transitive vertex merge sweep is replaced by find-or-insert on arrival.
So (b) measures the part where a shared graph would really contend, phases 2 and 3, and only that.

**Workloads.** One boolean each except the last, `Cut` in all three, tolerance 1e-7 mm.

- `array` (n = 32): 32 independent crossed-cylinder pairs from S1's random family, a third each ordinary, near-external and
  near-internal, placed apart in one pair of disjoint-union bodies. 128 + 128 faces, 145 candidate pairs.
- `comb` (n = 200, also 800 for contention): one long box through n plates, so each of its four long edges is hit by every
  plate. 6 + 1,200 faces, 1,600 pairs. Built to make edges hot. Classify is 80% of it, because S1's ray test has no index.
- `nurbs` (n = 16): 16 NURBS blocks cut by their tools, run one after another: a few very expensive pairs per boolean. One case
  ends in S1's `dangling-section`, in every shape.

**Machine.** Intel Core i7-8700K, 6 physical cores, governor `powersave`, single-core turbo above all-core turbo so speed-ups
read a little low (stated, not corrected). `rustc 1.99.0`, `RUSTFLAGS` empty, `x86_64-unknown-linux-gnu`, `lto = "fat"`,
`codegen-units = 1`. Pinned with `taskset -c 0-<n-1>`. Run with `rayon 1.12.0` through ordered `collect` only, one item per
task (`with_max_len(1)`); P11 measured a std-only pool within 1% of `rayon` on such maps. Each process runs on pool threads,
never the main thread (P11's correction). Seven repeats per configuration, minimum and median reported; the speed tables
are from one sweep, and comparisons are within it. Lock counters ran only in a separate sweep, so the speed runs carry
none. Output is hashed with `occam_math::Digest` twice: raw (every vertex, edge and face in the body's own order) and
order-free (sorted, so that a difference means geometry or topology). Twelve further repeats per count check determinism
(`array` n = 16, `comb` n = 120), on a build from before the two fixes below, which do not touch the output.

## Results

### Speed-up (median of 7, ms)

| workload | shape | 1 thread | 2 | 4 | 6 | speed-up at 2 / 4 / 6 |
|---|---|---|---|---|---|---|
| array | S1 serial | 92.0 | | | | |
| array | a | 94.4 | 47.4 | 26.5 | 18.8 | 1.99 / 3.57 / **5.02** |
| array | b | 92.6 | 47.2 | 26.1 | 18.8 | 1.96 / 3.55 / **4.91** |
| comb | S1 serial | 195.6 | | | | |
| comb | a | 203.0 | 108.5 | 60.3 | 43.2 | 1.87 / 3.37 / **4.70** |
| comb | b | 202.8 | 108.6 | 59.7 | 43.0 | 1.87 / 3.40 / **4.71** |
| nurbs | S1 serial | 233.1 | | | | |
| nurbs | a | 232.3 | 179.3 | 169.4 | 166.6 | 1.30 / 1.37 / **1.39** |
| nurbs | b | 234.4 | 176.3 | 166.8 | 164.5 | 1.33 / 1.41 / **1.43** |

The two shapes' wall times are within 1.9% of each other at every count on every workload (speed-ups within 2.9%). The spread between minimum and median is at most
2.8% everywhere. `array` runs 92 ms at one thread, a little under the protocol's 100 ms. Pure phases cost 2.6% and 3.8% over S1's
serial code at one thread on `array` and `comb`, and nothing measurable on `nurbs`.

For scale, P11 measured this machine's ceiling at 5.49x.

**Two mistakes that made the first sweep read low**, kept in `results/speed-before-prepare-fix.tsv` because they are lessons.
Trim polygons had been left serial in the preamble, outside every phase clock: 13.6 of 94 ms on `array`, which held it to 3.13x.
And `rayon`'s adaptive splitting left classify at 3.9x on `comb`, where bar regions cost hundreds of times what plate regions do;
one item per task gives 5.4x. P11 found the same about grain.

### Per phase at 6 threads (speed-up of the median)

| workload | shape | prepare | broad | pairs, or fused 2+3 | edge split | face split | classify | stitch |
|---|---|---|---|---|---|---|---|---|
| array | a | 4.81 | 4.05 | 4.96 | 3.47 | 5.15 | 5.38 | 0.89 |
| array | b | 4.78 | 4.45 | 5.06 | fused | 5.21 | 5.21 | 0.88 |
| comb | a | 2.13 | 4.44 | 4.34 | 2.26 | 2.87 | 5.37 | 0.97 |
| comb | b | 2.09 | 4.46 | 4.83 | fused | 3.00 | 5.36 | 0.94 |
| nurbs | a | 1.67 | 1.31 | 1.05 | 1.25 | 1.71 | 3.58 | 0.75 |
| nurbs | b | 1.15 | 0.84 | 1.12 | fused | 1.58 | 3.41 | 0.61 |

Taking phases 2 and 3 together, (a) reaches 4.69x on `array` and 3.97x on `comb` against (b)'s 5.06x and 4.83x. That is the only
place the shapes differ: (a) pays for its plan and merge, 0.4 ms on `array` and 1.7 ms on `comb` at six threads. It does not show
in the totals: (b) pays 0.2 to 1.2 ms of serial set-up and freeze instead, and the other phases are the same code. `nurbs` does not scale
in either shape because most of its time is a handful of marching sections per boolean, each one item to the pair-level map
and not divided by it (not isolated further; the 74% idle time in the maps is consistent with it).

Face split on `comb` stops at 3x, probably because four bar faces hold nearly all the work: the unit of work is one face, and a
large face is one task (reasoned from the shape of the workload, not isolated). Stitch is serial in both, by design here.

### Time lost

**(a), merge and plan.** Serial work is 0.2 ms on `array`, 2.0 ms on `comb` and 0.2 ms on `nurbs`, which is 1.2%, 4.7% and 0.1%
of the six-thread wall time. Idle time within the maps is 5.6%, 4.1% and 74% (`nurbs`, for the reason above). S3-P3 warned that
the merge is the thing to design and that real geometry might make it negligible: on this kernel-shaped work, it is negligible.

**(b), locks.** With counters on, at 6 threads (median of 7):

| workload | class | acquired | contended | waiting (ms) | share of fused thread-time |
|---|---|---|---|---|---|
| array n=32 | all classes | 1,869 | at most 0.7% | below 0.01 | below 0.1% |
| comb n=200 | edge | 14,400 | 2.4% | 0.16 | 0.4% |
| comb n=800 | edge | 57,600 | 2.7% | 0.59 | 0.4% |
| comb n=800 | section | 6,400 | 6.9% | 0.10 | 0.1% |
| comb n=800 | arena | 6,400 | 2.9% | 0.06 | under 0.05% |
| comb n=800 | vertex | 38,398 | 0.5% | 0.10 | 0.1% |
| comb n=800 | face | 12,800 | 0.5% | 0.01 | under 0.05% |

Even when four edges take every insertion, waiting is 0.4% of the fused phase. **Locks did not cost measurable time here**,
because intersecting costs much more than inserting. The case against (b) is not speed.

### Identical output

| workload | n | shape | raw digests at 1 / 2 / 4 / 6 threads | order-free digests at 1 / 2 / 4 / 6 |
|---|---|---|---|---|
| array | 32 | a | 1 / 1 / 1 / 1, all S1's | 1 / 1 / 1 / 1 |
| array | 32 | b | **1 / 1 / 2 / 4** | 1 / 1 / 1 / 1 |
| array | 16 | a | 1 / 1 / 1 / 1 | 1 / 1 / 1 / 1 |
| array | 16 | b | **1 / 1 / 5 / 5** (8 in all) | 1 / 1 / 1 / 1 |
| comb | 120, 200 | a and b | 1 / 1 / 1 / 1 | 1 / 1 / 1 / 1 |
| nurbs | 16 | a and b | 1 / 1 / 1 / 1 | 1 / 1 / 1 / 1 |

Shape (a) is bit-identical at every count (seven repeats per count on the speed sizes, twelve on the determinism sizes), and bit-identical to S1's serial result. Shape (b) gives
the same order-free digest as S1 every time, and on `array` a different **raw** output from run to run above two threads: the
order of vertices, edges or faces in the result depends on who won the locks (on an 8-thread laptop, 9 distinct raw digests in 15 runs at 6 threads and 10 in
15 at 8, `results/local-determinism.txt`). `comb` and `nurbs` happen not to show it: every comb region touches a face
boundary, so the walk that finds regions is ordered by the boundary, and a NURBS boolean has few pairs. That is an accident
of those shapes, not a property of (b). In these runs positions of merged vertices never differed, but nothing guarantees
that: with near-coincident points the first arrival becomes the vertex.

### What each can hand back when a pair fails (L5)

Two pairs were made to fail mid-task, after the pair's hits had gone into the shared edges in (b), and after phases 1 and 2 had
completed in (a). `results/l5-inject.tsv`, counts on the laptop, 8 repeats each.

| | (a) | (b), stop at the first failure | (b), keep going |
|---|---|---|---|
| failures reported, 1 and 6 threads | both, always | one at 1 thread; one or two at 6, depending on timing | both |
| work done when it stopped, `array` (145 pairs), 6 threads | all pairs reached the failing stage | 77 to 143 tasks | 143 tasks |
| work done, `comb` (1,600 pairs), 6 threads | all | **2 to 53 tasks**, 4 to 106 vertices | 1,598 tasks |
| the state | frozen phase outputs: candidates, sections, all hits, edge pieces, vertex table, each in a stable order, the same at any thread count | a graph whose content depends on timing, holding the failing pairs' hits, with no way to remove them | the same graph, with every other pair's work and the failed pairs' partial work: 1,600 vertices from 1,598 finished tasks |

Shape (a) reports every failing pair within the phase that failed, where S1 could report only one. The spike's report carries only the first pair and the count,
but the phase outputs are in scope and immutable at the point of return, so handing them back is a matter of returning them.
Shape (b) could hand back the graph, but what it contains would differ from run to run, and repairing or retrying needs an undo
that was not built.

### Code

| | Lines |
|---|---|
| S1's boolean | 1,133 |
| (a), the whole pipeline, including 75 of timing and map plumbing | 1,370 (+237); phases 2 and 3 go from 357 to 511 |
| (b), `shared.rs`, on top of (a)'s phases 1, 4, 5, 6 | 450, plus 88 it borrows from (a) (`clip_curve`, `edge_face_hits`): about 540 in place of (a)'s 511 |

The code is about the same size, and (b) is not finished: canonical order, undo and shared face splitting are all absent, and each adds
code. The shape of (a) costs little because it mostly moves a loop body into a closure; the two places that needed thought were the
plan for phase 2 and the stages of phase 3.

## Answer

**The kernel should take shape (a): pure phases, each an ordered map with a deterministic merge.** Not for speed: the two are
equal within noise (5.02x against 4.91x, 4.70x against 4.71x, 1.39x against 1.43x at six threads), and locks cost about 0.6% of
the fused phase across all lock classes, at worst, even with hot edges. It wins on the things that do differ. Its output is bit-identical at every thread count and
to S1's serial code, where (b)'s order varies from run to run (L23). It reports every failing pair and has frozen phase outputs
to hand back, where (b) stops at a timing-dependent point in a graph with no undo (L5). The code is about the same size, and (b)
would still need canonical order and undo.

**The winner does not differ by phase on anything that shows in the total.** Plainly: (b) is ahead by 8 to 22% on phases 2 and 3
taken alone, 0.4 to 1.7 ms at six threads, because (a) has a serial plan and merge there, and that does not show in total time.
The one phase whose shape is genuinely different is phase 3, which cannot be a single map:

**Data that must flow between phases**, frozen once written:

| From | To | What |
|---|---|---|
| Prepare | all | Per-face trim polygons; edge-to-face incidence |
| 1 broad | 2 | Candidate face pairs, in stable order. Bounds must be conservative (S1) |
| 2 pairs | 3 | Per distinct surface pair: curves, pinch points, coincident flag. Per distinct edge-against-face test: hits (edge, face, parameter, point) in plan order |
| 3 edge split, stage 1 | 3 clip | Per edge, its stops in parameter order; **a frozen vertex table with merges resolved**, so `find` is a read; hit to vertex |
| 3, between clip stages | 3 clip | Pinch vertices added and merged before any clip reads the table |
| 3 | 4 | New edges (curve, parameter range, end vertices), old edge to ordered pieces, section pieces (edge, face in A, face in B), vertex representatives |
| 4 | 5 | Regions: loops of directed new edges, parameter polygons, parent face and side |
| 5 | 6 | One label per region, in region order |

Phase 3 is therefore three rounds of map then merge (edges, pair events, clip), and the plan is the order: S1 mutated the vertex table while it clipped, and
pinch vertices must exist and be merged before any clip reads the table. Ids are given only in the merges. That one structural
change is what makes the output identical at every thread count.

## What this does not show

- A full shared graph. Phases 1 and 4 to 6 of (b) are (a)'s; faces were not split in place, and there is no undo or canonical
  order, so (b)'s real cost in code is more than 450 lines and its behaviour under a shared face split is unknown.
- Better concurrent designs: lock-free structures, atomics, per-thread bump arenas, or ownership by region.
- Large bodies. S1's bodies are small: `array` and `comb` are concatenations, and `comb` has edges hit by only 400 pairs per edge
  at n = 200 and 1,600 at n = 800.
- Anything beyond S1's limits. Classify is quadratic in faces; a spatial index would shift the phase balance.
- Parallelism inside a pair. `nurbs` shows the need: a section that dominates a boolean is one item to this map.
  That is `proving-ground.p4` and `p5`.
- Phase 6, the serial vertex sweep in phase 3, and parallel versions of them, which were not tried.
- Memory, wasm, more than six cores, or hyperthreads. Only `Cut` was run in each workload.
- That the injected failures match real ones: they mark a mid-task failure, and the spike's `Report` is not extended.
- The determinism sweep ran before the two fixes above. They change speed, not output: the later speed sweep's digests agree.

## What it decides

For `proving-ground.design`, as proposals to confirm there:

- The boolean is a sequence of pure phases, each an ordered map from frozen input to frozen output, on the P11 `map` interface
  with one item per task. Ids are assigned only in merges, as S3-P3 proposed.
- Phase 3 is planned as stages with a frozen vertex table between them, and the preamble is a phase of its own.
- Failures are collected per item and reported in candidate order, so a partial result is a set of named frozen outputs plus every
  failing pair.
- Nothing in the kernel's boolean needs a mutex for speed. The shared-graph shape should be set aside rather than kept in
  reserve; its one measured advantage is at most 1.7 ms in phases 2 and 3.

## Open questions for the user

None. The choice of shape follows from the brief's requirement of the same bits at any thread count and from L5.
