# `proving-ground.p8`: how much work can be avoided? (L27)

Spike on the never-merged `spike-p8` branch, 2026-11-09. Code is in `spikes/p8/`, a copy of S1's boolean with counters and
switches added. Raw output and the commands are in `spikes/p8/results/`. S1's limits carry over to everything here: see
S1's finding (`2026-11-09-s1.md`).

## Question

Of the work S1's boolean does, how much can be avoided by tighter bounds, by computing only the derivatives needed, by
content-addressed caching of intersection results, and by recomputing only what an edit changed, separately and together? Which
are worth building first?

## What was measured

**Counts first, timings where counts cannot answer.** Most figures are counts made on the laptop under the memory cap,
single-threaded, which load cannot disturb. The unit is an *evaluation*: one call of a surface evaluator, implicit function,
closest-point projection, or curve point or tangent, counted only while a boolean runs, so case set-up and volume measuring do not
count. Calls differ in cost, so an evaluation count is a proxy for work and not a time. Where a phase share is needed to weight
the counts, the weights are local phase timers: indicative only, and marked. A short set of timings was then taken on the measuring
machine through `spikes/tools/remote.sh`: an Intel Core i7-8700K, 6 physical cores, governor `powersave`, rustc 1.99.0, `RUSTFLAGS`
empty, target x86-64 Linux, pinned with `taskset -c 0`, 7 repeats, counters and digests off inside the clock. Minimum and median
differ by under 0.5% in every row. A first timing pass, with the counters left on, overstated the time and is not reported.
Instruction counts were not taken: valgrind stops with an illegal opcode in the dynamic loader on this machine.

**Workloads.**

- *Corpus:* the 546 cases of `tools/corpus/generated/`, as S1 ran them, at 1e-7 mm (468 answered, 32 reports, 46 not supported).
- *NURBS:* 12 of S1's generated blocks, each as common, cut and fuse, 36 operations.
- *Random:* 20 of S1's crossed-cylinder pairs, 60 operations.
- *Part:* new for this spike. A plate of N through holes (N = 4, 8, 16, 32), one boss fused through it and one spherical dimple
  cut in it, built as N + 2 successive booleans, each taking the last result as its input. Holes have varied radii and positions.
  Also a NURBS block cut by three planes in turn.

**Edits to the part:** none (a re-run), one hole's radius, one hole moved, the first hole, the last hole, the last feature, and the
plate's thickness, which every later step depends on.

**Each result was checked.** Every boolean's output is digested (bits of every vertex, edge, curve, face and surface, through
`occam_math::Digest`). A switch that avoids work must leave every digest of every case unchanged, or it is counted as a mismatch.
This is L23's requirement, applied to the whole chain.

**Prior art.** Separating-axis and implicit-sign culling are standard; the convex hull and local support of a B-spline are Piegl
and Tiller, *The NURBS Book*, chapter 3. Keys of the kind used here are the idea of content-addressed storage in general. The
book's contents were checked on 2026-11-09, and the passage was not re-read.

## Results

### 1. Bounds culling

Against S1's broad phase, which boxes each face and tests boxes pairwise. Levels are cumulative. *Tight* replaces the boxes with
analytic or trim-aware ones. *Edge box* also skips an edge-against-surface scan when the edge's own box misses the other face's
box. *Implicit* also skips a pair or an edge when the other surface's implicit function cannot change sign over the box, and tests
a plane against a NURBS's control points. *Floor* is not a method: it replays only the face pairs a first run found to contribute
a hit or a kept section piece, which bounds what a pair-level test that keeps every contributing pair could do. It is a sufficient
set found in one traversal order, not a proved minimum.

| | implicit | 1408 (-13%) | 692 (-16%) | 1630 (-78%) | 10.36M (-35%) | 13.28M (-40%) | 0 |

| | edge box | 189 | 189 | 291 (-76%) | 3.25M (-8%) | 0.55M (-31%) | 0 |

| | floor | 153 (-19%) | 153 (-19%) | 1050 (-13%) | 3.50M (-1%) | 0.75M (-6%) | 0 |

| | floor | 162 (-42%) | 54 (-36%) | 1014 (-35%) | 2.74M (-8%) | 3.19M (-13%) | 0 |

Three things stand out.

**Tighter boxes alone are almost worthless here.** They remove 0.2% of the corpus's pairs. S1's boxes are already close to exact for
planes and cylinders. The 5% fewer surface evaluations at this level are the cost of S1's sampled boxes themselves.

**The unit that matters is the edge, not the pair.** S1 scans every edge of a face against the other face's surface, and the scan
is the expensive part (64 to 512 samples, then bisection for each extreme and root). A box test per edge removes 66% to 76% of the scans, which is
more than a perfect pair-level oracle does (13% to 35%). The floor's edge-scan count is high because it only removes pairs; it says
nothing against edge-level tests.

**A wrong bound fails loudly here, but it could fail silently.** My first tight cylinder box had a mis-ordered minimum, which made
some boxes too small. At the tight level 31 corpus cases changed, each from an answer to a `dangling-section` report, all in the
near-tangent and Steinmetz families. At the edge-box and implicit levels 54 changed (the same box, plus `pair-failed` and
`classify-inconsistent`). None returned a wrong answer here, but only because a later phase happened to trip, and S1 saw the same
class of error pass silently (its finding: "bounds must be conservative"). A culling test has to be conservative and also covered by
a digest comparison against the unculled run. With the bug fixed no digest changed at any level, and every figure in the table is
from the fixed code.

On NURBS the implicit level matches the floor's 153 pairs. Which of its tests removed them was not separated.

**Timed on the measuring machine** (median of 7, whole run including building the primitives, digests off): culling alone takes the 216
near-crossed cases from 307 ms to 260 ms (-15%) and the 36 NURBS operations from 502 ms to 491 ms (-2%). NURBS barely moves because
its cost is the marching section, which culling does not touch.

### 2. Only the derivatives needed

**What the question asks about does not occur here.** S1 has no evaluator for second derivatives, so none are computed, and
`Surface::normal` is called zero times in any boolean. The one normal S1 forms (the height of a point above a NURBS) is used. That is
a limit of the prototype, which has no curvature-driven step, no fillet and no meshing: it says nothing about whether a kernel with those
would compute second derivatives it does not use. What S1 does waste is first derivatives, in three places:

| where | corpus | NURBS 36 ops | random | computed and dropped |
|---|---|---|---|---|
| NURBS point queries that receive `Su` and `Sv` too | none | 1,574,406 of 2,970,507 evaluations (53%) | none | two first derivatives |
| a trim polygon's points, where `on_surface` computes a parameter rate per sample | 4,196,792 | 109,317 | 1,046,718 | `surface.derivs`, `curve.deriv` and a 2x2 solve, on every analytic sample. Every such call in a boolean drops the result |
| bisection for a root, where the `value, slope` pair is computed and only the value read | 506,326 | 95,508 | 80,718 | one curve tangent each |

The trim polygon case is the largest and was found by reading the callers, not by the first counters.

Removing all three, with every digest unchanged:

| workload | surface evaluations | curve evaluations | whole-run time, median of 7 |
|---|---|---|---|
| corpus | 15.95M to 11.75M (-26%) | 22.20M to 17.49M (-21%) | near-crossed, 216 cases: 307.1 ms to 202.9 ms (-34%) |
| NURBS | 3.52M to 3.34M (-5%), and 53% of those are about half price | 0.80M to 0.60M (-26%) | 501.8 ms to 336.2 ms (-33%) |
| random | 2.98M to 1.94M (-35%) | 3.68M to 2.55M (-31%) | not timed |

A point-only NURBS evaluation costs 48.6% of `eval_ders` (154.9 ms against 318.8 ms for two million, with identical digests), so the
derivatives are about half of a point query's work. The NURBS workload's evaluation count hardly changes while its time falls by a
third because the same calls became cheaper.

**Most of this is S1's own sloppiness, not a law of kernels.** The trim polygon waste exists only because `on_surface` returned rates
to everybody, which a kernel designed with a parameter-only query would never do. The number that generalises is the shape of it: an evaluator
that always returns more than the caller wants pays for it on every call, and the calls that want less are many. A single evaluate-to-order-2
entry point would have been worse: by contraction count (Piegl and Tiller, A3.6 and A4.4) it costs about six tensor contractions per
point against three for first derivatives and one for the point alone, which is an estimate and not measured.

### 3. Content-addressed caching of intersection results

A cached entry stores what `section` and `hits` return. The key is the content of the inputs, bit-exact: each surface's kind and
every defining number, chart frame included (for a NURBS the degrees, counts, knots and control points), the pair in order, both
tolerances, and for a `hits` entry the curve and its parameter range. No reuse changed any digest in any of the 28 part-edit runs,
at any size.

**Hit rate and work saved on the part** (cache primed by the first build, N is the number of holes, percentages are of lookups and
of the recomputed run's evaluations):

| edit | section hits, N = 4 / 8 / 16 / 32 | edge-scan hits, N = 4 / 8 / 16 / 32 | evaluations saved, N = 4 / 8 / 16 / 32 |
|---|---|---|---|
| re-run, nothing changed | 100 / 100 / 100 / 100 % | 100 / 100 / 100 / 100 % | 27 / 28 / 30 / 30 % |
| middle hole's radius, or moved | 83 / 90 / 94 / 97 % | 84 / 90 / 95 / 97 % | 22 / 25 / 28 / 29 % |
| first hole's radius | 83 / 90 / 94 / 97 % | 84 / 90 / 95 / 97 % | 22 / 25 / 28 / 29 % |
| last feature | 83 / 90 / 94 / 97 % | 88 / 92 / 95 / 97 % | 23 / 26 / 28 / 29 % |
| plate thickness (every later step sees it) | 42 / 45 / 47 / 49 % | 52 / 58 / 64 / 69 % | 13 / 17 / 19 / 21 % |

On the NURBS block cut three times, moving the second plane: 9 of 14 sections hit (64%), 52 of 92 scans hit (57%), and 19% of the
evaluations were saved.

**A high hit rate does not mean a large saving.** A 97% hit rate saves 29% of the evaluations, because intersections are all this
cache can avoid. The other 70% is face split, trim polygons and classification, which depend on the trimmed input and are not
cached here. A re-run, the best case, saves 30%. **Hit rates rise with N** because one changed feature is a smaller share of the
surface pairs; that is the only scaling this part shows.

**What the key has to hold, and what happens if it does not:**

| omitted from the key | test | digests changed | outcome changed | what went wrong |
|---|---|---|---|---|
| nothing (the correct key) | every test below | 0 | 0 | control |
| the tolerance | 306 near-tangent corpus cases run at 1e-7 mm, then through the same cache at 1e-2 mm | 74 | 15 | `near-crossed-external-0012-intersection`: recomputed at 1e-2 the common volume is 0; through the cache it is 5.81e-4 mm^3, the lens that exists at the other tolerance |
| the edge's parameter range | a plate notched twice on one edge, so one curve has two pieces | 0 | 1 of 1 | recomputed answers 9216.73 mm^3 (the closed form); through the cache the second piece reuses the first piece's hits and the boolean fails with `loop-not-closed` |
| rounding, coordinates to 1e-6 mm | two crossed cylinders 6e-7 mm apart in offset | 1 of 2 | 1 of 2 | overlapping by 3e-7 mm after separated by 3e-7 mm: recomputed lens volume 2.3e-12 mm^3, through the cache none, the lens is lost |
| the argument order | 4 crossed-cylinder pairs, A against B then B against A | 0 | 0 | no difference in these 4 (why was not examined). Not shown to matter; kept in the key because it costs nothing |

So a correct key holds the surfaces' kind and every defining number in order, the tolerances, and for an edge scan the curve and its
range. It holds them bit-exact: rounding to gain hits is exactly the near-tangent case. **It must also hold the code version and any
switch that changes numerics (L23).** This was not run: S1's toggles are read once per process, so one run cannot flip them. They do
change section curves, so a key shared across builds would return another build's curves.

The trim is deliberately not in these keys. `section` and `hits` read only the untrimmed surface and the curve, and the trim is applied
afterwards by `locate` and the clipping, which are not cached. A cache at the level of a clipped section piece would have to include the
trim, or it would hand a piece from one face to another.

**A hit must not change the code path.** A cached section holds the `Arc<Nurbs>` of the run that made it. `Curve::on_surface` asks
`Arc::ptr_eq` to decide whether a curve's stored parameters apply. Content-equal but pointer-different therefore silently takes
the closest-point path. On the NURBS block that made the *cached* run 4.7 times more evaluations than recomputing (1.50M against 317k,
with the same section and scan hit counts), with digests still equal. A cached result has to be re-bound to the surface of the
current run, which is what every figure in the table above does. The lesson generalises: identity by pointer and identity by content
cannot be mixed in one kernel.

The key in this prototype compares surface bytes exactly, but reduces a curve to a 64-bit FNV digest of its printed form. No collision
was seen at this size. A kernel would need a stronger hash or a byte comparison on hit. The cost of building and hashing the keys
was not measured.

### 4. Recomputing only what changed

After one edit, how much downstream work has to be redone? Two levels were counted. *Step-level* reuse skips a boolean whose two
inputs, operation and tolerance are bit-identical to one already done, the granularity a feature tree gives for free. *Item-level*
reuse skips any single piece of work (one section, one edge scan, one face split, one region's classification) whose input content
was already seen, across the whole previous build. Each item is keyed by the content of its inputs: its faces and curves by value,
not by this run's numbering.

**Only step-level and the pair caches were actually executed.** Item-level reuse of face split and classification was counted, not
built, so its digest equality is not demonstrated. A real implementation would have to re-base the numbers of the edges and vertices in
a cached region onto the current run. The figures are the fraction of items whose key was not seen before: an upper bound on
what could be skipped, and an honest count of the dependencies.

Fraction of the work redone after one edit on the part, weighted by each phase's share of a local run. The phase weights are indicative,
the count fractions they weight are not:

| edit | step-level reuse, N = 4 / 8 / 16 / 32 | item-level reuse, N = 4 / 8 / 16 / 32 |
|---|---|---|
| last feature | 20 / 13 / 8 / 4 % | 9 / 6 / 3 / 2 % |
| last hole's radius | 59 / 39 / 24 / 14 % | 23 / 13 / 7 / 4 % |
| middle hole's radius, or moved | 75 / 71 / 71 / 71 % | 27 / 21 / 14 / 10 % |
| first hole's radius | 100 / 100 / 100 / 100 % | 37 / 30 / 22 / 16 % |
| plate thickness | 100 / 100 / 100 / 100 % | 85 / 85 / 85 / 85 % |

The middle-hole row, by class of item, at N = 4 and N = 32: sections 17% and 2.9%, edge scans 26% and 5.4%, face splits 20% and 5.1%,
region classifications 41% and 15%.

**Why step-level reuse is so much weaker than item-level:** every later step takes the previous result as an input, and an early edit
changes the bits of that result, so a feature tree alone reuses nothing after an edit (0 of 34 steps for the first hole). The later steps
are also the heaviest, because the body has grown. Only a finer key notices that the plate's far-away faces did not change.

**Why classification lags:** a region's label depends on every face of the other body, because a ray can reach any of them, so its key
includes a digest of the whole body. Any edit invalidates all classification on that body, which is why the thickness edit redoes 100% of
it and why classification has the highest redone fraction of any class in every row. Broad phase, edge split and stitch have no finer
key than the step, so they are counted at the step-level fraction in both columns. A narrower dependency, per ray and per face reached, was
not tried.

**The edit that touches everything is still 85% of the work at item level.** A change to plate thickness moves every top and
bottom face and every hole's trim, so most keys change. Incremental rebuild is not free of the shape of the edit.

### Together

Everything on at once, on the part with 32 holes, editing the middle hole's radius, and timed with 16 holes on the measuring machine
(median of 7, first build included in the cache rows' priming and left off the clock):

| configuration | evaluations (N = 32) | time (N = 16) | digests |
|---|---|---|---|
| recompute, S1 as it is | 27.19M | 158.6 ms | |
| content-addressed pair cache | 19.21M (-29%) | 124.9 ms (-21%) | identical |
| culling and only the derivatives needed, no cache | 10.48M (-61%) | 77.9 ms (-51%) | identical |
| culling, derivatives needed and the cache | 10.40M (-62%) | 77.8 ms (-51%) | identical |

And on a first build, on the corpus, culling and needed-only together take surface evaluations from 15.95M to 6.16M (-61%) and curve
evaluations from 22.20M to 8.70M (-61%). The 216 near-crossed cases take 307.1 ms to 156.6 ms (-49%), the 36 NURBS operations 501.8 ms to
327.6 ms (-35%).

**On analytic parts the cache adds almost nothing once the cheap methods are on.** Culling removes the scans and needed-only makes
the rest cheaper, and those are what the cache would have removed: 77.9 ms against 77.8 ms. **What remains is the work the pair cache
never touches:** face split, trim polygons and classification. Recomputing only what changed would reach it, but that is the part
that was counted and not built.

## Answer

Worth building, in this order:

| order | what | work avoided (first build unless stated) | complexity | verdict |
|---|---|---|---|---|
| 1 | An evaluator with explicit order, and a parameter-only query | 33% to 34% of whole-run time on the two workloads timed; half of a point query | Very small, but it is an API, so it has to be there from the start | **Do first.** Most of the size here is S1's own waste, but the fix is free and cannot be retrofitted cheaply |
| 2 | A box test (then an implicit-sign test) per edge before every edge-surface scan, with the bound conservative and digest-tested | 66% to 86% of scans; 15% of time on near-crossed, 2% on NURBS; with (1), 49% and 35% | Tens of lines. The risk is a bound that is wrong | **Do first.** Tighter face boxes alone are not worth doing: they removed 0.2% of pairs |
| 3 | A content-addressed cache of intersection results | 97% hit rate on an edit at 32 holes, 57% to 64% on the NURBS block; 21% of time at 16 holes before (1) and (2), about 0% after them | Moderate: canonical keys, version in the key, re-binding on a hit, eviction | **Build for expensive intersections only**, when marching on NURBS pairs exists. It earns nothing on closed-form sections once (1) and (2) are in |
| 4 | Recompute only what changed, at the level of a face, region or edge scan | After a mid-tree edit, 90% of the downstream work at 32 holes (73% at 4), against 29% from step-level reuse; 15% for a thickness edit | Large: stable content keys on faces, cached outputs re-based onto this run's numbers, classification's whole-body dependency | **Design for it now; build it after the kernel settles.** Make each phase a pure function of content, with no run-specific ids in its output |

Step-level memoisation by feature is cheap but weak: after a mid-tree edit it still redoes 71% of the work, because every later step's input has changed. It is worth having
as the first slice of (4), not as a substitute for it.

Results reused gave the same digest as recomputing in every run where a cache was on, 28 part edits plus the NURBS chain, provided the key is
complete and a hit re-binds pointer identity. Keys that were too narrow changed digests or outcomes, and one returned a volume from
another tolerance.

**S1's corpus limits this a great deal, and the direction of the limit differs by method.** A corpus case is two bodies of a few faces to a few
tens of faces, and the largest part here has 34 booleans and a plate with 32 holes: real parts have thousands of faces and repeated features.

- Culling should matter more at scale, because S1's broad phase is all-pairs and the edge scans grew 21 times from 4 holes to 32, faster
  than the part. But S1's broad phase is also the first thing a real kernel would replace with a hierarchy, and the absolute saving would
  change with that. Not measured.
- Needed-only derivatives are the least affected by size: their percentage depends on the mix of queries.
- Caching: hit rates rose with N, from 83% to 97%, and there is no reason to expect them to fall. But this part has no repetition: holes
  differ in radius and position. A pattern of equal holes gets no hits across instances from a key on absolute coordinates; a key in a
  local frame would, but would no longer be bit-identical to recomputing (L23), so it is a separate decision. Not measured.
- These parts have no marching against another NURBS, no cones, tori, fillets or coincident surfaces: the intersections are cheap
  closed forms, which understates the cache's value and overstates the culling's. A part dominated by NURBS sections would rank the cache
  much higher. The NURBS numbers (64% of sections hit, and culling worth 2% of time) are the only hint of that.

## What this does not show

- Anything about parallel speed-up: everything is single-threaded. How a shared cache behaves under threads, and whether it needs locks,
  is not touched here.
- That face split and classification can actually be reused. Their item-level figures are counted from keys and were never executed, so no
  digest shows they would agree (L23). The pair caches were executed and checked.
- Memory: the cache's size, and any eviction policy. The caches here held up to a few thousand entries at 32 holes.
- The cost of hashing keys. It is not in the evaluation counts, though the part timings do include it.
- Second derivatives and normals. S1 has no code that would use or waste them.
- Pattern repetition and instancing across parts. The content key cannot share across positions; a local-frame key was not tried.
- Determinism across machines: digests were compared within one build on one machine, or between configurations of one binary. The
  cache is unsafe across builds unless the key includes the code version, as L23 demands, and that was argued rather than run.
- That the bounds are conservative beyond these cases. The tests were checked by digest equality on the 546 corpus cases and the
  generated families. The first attempt had a bug that only the corpus exposed.
- That the ranking holds for real parts. S1's limits (no cones, tori, fillets or coincident surfaces; simple surfaces; small bodies)
  apply, and the part used to measure edits is synthetic.
- The ranking's time figures come from S1's phase split, which depends on S1's naive face split and all-rays classification. A kernel
  with flood-filled classification would shift them. Flood-fill was not measured, though classification is about a sixth of the part's local phase time.

## What it decides

Nothing is decided here: this is evidence for `proving-ground.design` and the document layer. It supports these inputs:

- `occam-math`/geometry API: evaluation by explicit order (point; point and first derivatives; and so on), and a parameter-only query for
  curves on surfaces. No single evaluate-everything entry point.
- Boolean design: an edge-level bound before each expensive edge-surface scan, with the bound conservative by construction and a
  digest test against the unculled run in the test suite.
- Document layer: each phase a pure function of content, with no run-specific numbering in cached outputs, so that item-level reuse is
  possible later. Identity is by content, never by pointer.
- Cache: a key made of the surfaces' defining bits in order, both tolerances, for edge scans the curve and its range, and the code version.
  No rounding in the key.
