# Finding: `proving-ground.p4`, how do threads and SIMD lanes nest?

Code: `spikes/p4/` on branch `spike-p4`. Raw output is in `spikes/p4/results/`. `spikes/p4/run-sweep.sh <name>` is the
command behind each file (table at the end of this section), and `spikes/p4/tools/report.py` regenerates every table below
from those files.

## Question

For the kernels a CAD kernel spends its time in, which lane width pays, does `Lanes<W>` (plain arrays under
`forbid(unsafe_code)`) get there alone or is `fearless_simd` worth asking for, and what is the rule for nesting threads and
lanes (L28, L29, L30)?

## What was measured

**Machine.** Intel Core i7-8700K, 6 physical cores (12 logical), governor `powersave`, single-core turbo above all-core
turbo, so speed-ups read a little low; this is stated and not corrected for. L1d 32 KiB and L2 256 KiB per core, L3 12 MiB
shared. Threads pinned with `taskset -c 0-<n-1>`, so only physical cores are used. `rustc 1.99.0`, `wasmtime 49.0.2`,
release profile `lto = "fat"`, `codegen-units = 1`.

**Targets.** Three builds, named as the `label` column of every file: `base` is x86-64 with no flags, so SSE2 for anything
the compiler vectorises, and the only build `docs/DETERMINISM.md` rule 5 allows. `v3` is `-C target-cpu=x86-64-v3` (AVX2 and
FMA). `wasm` is `wasm32-wasip2` with `-C target-feature=+simd128` under `wasmtime`. `v3` is measured to separate what the
instruction set buys from what the compiler does with it. It is not a candidate build.

**Protocol.** Every timing went through `spikes/tools/remote.sh`, one at a time on the quiet machine. Each configuration is
one process running seven repetitions after one discarded warm-up; tables give the minimum unless they say otherwise, and
the median is in the raw files. Two exceptions: `levels.csv` is a three-repetition check of the bits, so its times are only
indicative, and the hand-written scalar crossing test has no warm-up run. Output is hashed with `occam_math::Digest` after
the clock stops. Each results file records the CPU, governor, `rustc --version`, `RUSTFLAGS` and size in its header.

**Kernels**, each written once over a number trait (`spikes/p4/src/num.rs`), so every width runs one formula:

- `bspline`, the reference workload: bicubic B-spline surface over a (u, v) grid, FindSpan, BasisFuns and SurfacePoint
  (Piegl and Tiller, *The NURBS Book*, 2nd ed., 1997, A2.1, A2.2, A3.5; the basis recurrence is de Boor's, *A Practical
  Guide to Splines*, 1978). `bspline_clamped` removes the bounds checks with clamped indices.
- `bspline_grid`: the same surface organised around the grid, with spans and basis functions once per row and column. Size
  `bezier` is one Bézier patch per face, so nothing is gathered.
- `nurbs_d1`: rational surface with first derivatives and unit normal (A2.3, A3.6, A4.4).
- `analytic`: cylinder and sphere point and normal from precomputed `sin`/`cos`.
- `bounds`: bounding box of a control patch and an overlap test: masks and reductions.
- `crossing`: point in polygon by crossing number (Shimrat, CACM 5(8), 1962), branching per lane on every edge.
  `crossing_any` skips an edge's division when no lane straddles it.

**Variants.** `f64`; `l2`...`l16` for `Lanes<W>`; `fs`, the same kernel over `fearless_simd` 1.2.0 at the width its level
picks (AVX2 gives 4 lanes, simd128 gives 2); `fsfma`, the same with `a * b + c` fused; `d4` and `d8`, plain `Lanes<4>` and
`Lanes<8>` inside `fearless_simd`'s `dispatch!`, so plain arrays get AVX2 from a `base` build. `fs` and `d*` run at the level
`Level::new()` picks at run time, which is AVX2 on this machine even in a `base` build.

**Nesting.** `std::thread::scope` with a mutex over the face iterator; threads claim whole faces, about sixteen claims per
worker, and each face writes only its own output slice.

**Sizes.** `small` is 64 faces of 78 KB each for `analytic` (976 points), and 64 by 64 grids for the spline kernels;
`l1` is 244 points per face for `analytic`, 19 KB of input and output together; `p<N>` sweeps the points per face;
`large` exceeds the 12 MiB L3 (3.1 GB for `analytic`); `fs` is one face shared between threads.

## Results

### Determinism

Every digest agrees. Over 741 timed configurations in the result files, grouped by kernel and problem size into 36 groups,
each group has one digest, across thread counts 1, 2, 4 and 6, `f64` and every lane width, `base`, `v3` and `wasm`, and
`fearless_simd` at SSE2, SSE4.2, AVX2 and simd128. Run `tools/report.py digests` over the CSV files other than `slp.csv`.

`fsfma` is the one exception, and it is the expected one. On AVX2, fused `a * b + c` changes the digest of every kernel that
uses `madd` (`analytic`, the spline kernels, `nurbs_d1`), and leaves `bounds`, `crossing` and `spans` alone because they
have none. On simd128, SSE2 and SSE4.2 there is no fused instruction, and the digest stays that of the unfused kernel.
`fs` without fusion is bit-identical to `Lanes<W>` everywhere it ran.

What this shows:

- **The reference workload barely benefits.** `bspline` gains at most 1.19 on `base`, from `Lanes<2>`, and 1.02 to 1.07 from
  `fs` and `d4` at AVX2. The two FindSpan searches and the per-lane gathers are scalar work that lanes cannot share (`spans`
  alone is 6.9 ns of its 46.9 ns). Bounds checks cost lane code as well: `bspline_clamped` gains 1.21 to 1.37 where `bspline`
  gains 0.82 to 1.07 (`l4`, `l8`, `d4` and `fs`).
- **Organising the kernel around the grid beats widening the lanes.** `bspline_grid` is 1.5 times faster than `bspline` in
  plain `f64` (31 ns against 47 ns), before any lanes. When nothing is gathered (`bezier`), lanes pay 1.8 to 1.9 on `base`,
  2.0 to 2.1 through `dispatch!` in the same build, and 3.3 in a `v3` build (the next section has the gap between those two).
- **`Lanes<2>` is a trap for straight-line per-point work.** `analytic` at W=2 is 0.38 of scalar on `base`, 0.32 on `v3` and
  0.45 on `wasm`: not a gain but a 2.2 to 3.1 times loss.
- **Masks and reductions pay most, at W=8:** `bounds` 3.0 on `base`, 5.8 on `v3`, and `crossing` 2.6 and 4.7. On `wasm`
  W=4 to 16 are close, with no clear winner: `bounds` 3.9, 3.4 and 4.5, `crossing` 2.5, 3.3 and 3.8. Skipping work with
  an "any lane" test (`crossing_any`) pays less than doing every lane's work, because most lanes straddle some edge
  anyway.

### What vectorised

`results/asm-*.txt` counts packed and scalar floating-point instructions per function, for `base`, `v3` and `wasm`.
`packed` here also counts shuffles and blends, so read it as "vector code exists", and `scalar` as arithmetic left scalar.

The surprising cases:

- **`analytic` at W=2 is scalar.** `Lanes<2>` has 65 packed against 225 scalar on `base`, 45 against 225 on `v3`, 100 against
  225 on `wasm`; W=4 has 158 against 135. Plain `f64` here is loop-vectorised (65 packed against 45 scalar), which is why
  `f64` is the number W=2 cannot beat. `results/slp-asm.txt` (below) shows the same thing with a smaller cylinder kernel.
- **`nurbs_d1` at W=4 is 2.3 times slower than scalar because `array::from_fn` was not inlined.** The function holds four
  out-of-line calls to `core::array::try_from_fn` at W=4 and W=8 and none at W=2, and moves vector registers to or from
  the stack 298 times at W=4 (`results/asm-calls.txt`). Replacing `std::array::from_fn` in `Num::gather` by a plain loop (`--cfg p4_gather_loop`,
  `gather.csv`) turns it around: 208 to 87 ns on `base` (0.44 to 1.07 of scalar), and 201 to 81 ns on `v3` (0.45 to 1.12).
  So this is an inlining effect of one library call, measured with only that line changed, and the digests are unchanged.
  `occam-math`'s `Real::from_fn` for `Lanes<W>` uses the same call.
- **The same AVX2 kernel is not always equally fast.** On the Bézier workload `d4` is 8.8 ns/pt in a `v3` build and 15.7
  ns/pt from `dispatch!` in a `base` build, `fs` 8.6 and 14.8, and plain `l4` in a `v3` build 15.4, although `l4` and
  `d4` are both `Lanes<4>` compiled with AVX2. `bounds` and `crossing` have no such gap (`d8` 7.0 and 6.7 ns on
  `bounds`, 27.7 and 27.4 on `crossing`). I did not establish why.

### Plain arrays against `fearless_simd`

- **What it needs.** The kernel source stays under `#![forbid(unsafe_code)]`: `spikes/p4` compiles with it, and
  `dispatch!` is safe to call. `fearless_simd` keeps a little `unsafe` inside its own crate. Runtime selection is
  `Level::new()` once, then `dispatch!`, which instantiates the closure for each compiled level (SSE2, SSE4.2, AVX2,
  AVX-512 on x86-64). The chain from the dispatch closure to every leaf must be `#[inline(always)]`, or the leaf is
  compiled without the target features (the crate's own `MANUAL_INLINING.md` says so). On wasm, simd128 is a
  compile-time choice. It is Apache-2.0 OR MIT with a dependency-free core, version 1.2.0, MSRV 1.89.
- **Bits.** `fs` is bit-identical to `Lanes<W>` as long as nothing fuses, including at AVX2 (`levels.csv`). Its `mul_add`
  changes bits on AVX2 and is out of bounds under `docs/DETERMINISM.md` rules 2 and 5.
- **Speed.** On `base`, reaching AVX2 at run time is worth a great deal for mask kernels: `bounds` from 3.0 (`l8`) to
  5.9 (`d8`), and `crossing` from 2.6 to 3.9. `Lanes<W>` under `dispatch!` (`d4`, `d8`) gets most of that with no change
  to the kernel. Explicit `fs` is better than `d4` for `analytic` at L1 size (1.46 against 1.03), `crossing` (3.95
  against 3.18) and `nurbs_d1` (1.10 against 0.45, the `from_fn` issue), but worse for `bounds` (2.26 against 4.66 and
  5.94). On `wasm`, plain lanes beat `fs` for `bounds` (3.2 to 4.5 against 1.41) and, from W=4 up, `crossing` (2.5 to
  3.8 against 2.1), and neither beats scalar `f64` on `analytic` (`fs` 0.55, best plain 0.71).
- **`dispatch!` from a `base` build does not always reach a `v3` build's speed.** It does for `bounds` and `crossing`,
  and not for the Bézier workload or `analytic` (`d4` 1.39 ns/pt in a `base` build at L1 size, 0.80 in a `v3` build).
- **Width is not always better.** `levels.csv` has `fs` for `bspline_grid` at 20.2 ns/pt on SSE2 (2 lanes), 23.1 on SSE4.2
  (2 lanes) and 23.6 on AVX2 (4 lanes).

3.7 to 4.1 at six, against 5.3 at six for `bspline_grid` in the same runs. `base` is mixed: `f64` is normal (5.27), and the
lane variants other than `l2` reach 4.1 to 4.6 at six.

per 30 ns, scales normally.

### False sharing

`false-share-1.csv` (`analytic`) and `false-share-2.csv` (`bspline`) have six threads writing to one face's columns in
slots of `chunk` points, alternating between threads, one face of 262144 points (`analytic`) or 65536 (`bspline`).
Minimum ns per point:

| chunk (points) | bytes | analytic f64, 6 threads | analytic l4, 6 threads | bspline f64, 6 threads |
|---|---|---|---|---|
| 1 | 8 | 23.04 | - | 12.66 |
| 4 | 32 | 10.27 | 9.84 | - |
| 8 | 64 | 8.03 | 7.95 | 9.36 |
| 64 | 512 | 4.25 | 4.14 | 8.85 |
| 512 | 4096 | 3.29 | 2.93 | - |
| 4096 | 32768 | 2.88 | 2.50 | 9.96 |

At one thread, `analytic` at chunk 1 costs 24.04 ns per point and `bspline` 52.27. So at chunk 1, six threads give `analytic`
a speed-up of 1.04 and `bspline` 4.1. The chunks are not cache-line aligned, so an 8-point (64-byte) chunk still shares two
lines with its neighbours. For `analytic`, data at this size is beyond L3, so the numbers above chunk 512 are the memory
ceiling, not false sharing. For `bspline`, chunks of 8 points or more are indistinguishable from 4096. The penalty needs a
high write rate as well as sharing; the kernel that writes most per second suffers most.

### The bimodal timings of `analytic`

At 76 KiB per face, the `small` size, `analytic` runs in one of two states, for example `d4` at about 1.44 or 3.23 ns
per point and `l4` at about 1.93 or 2.97. The cache sweep shows the same levels at larger sizes. Seven repetitions of
one process usually agree, but two processes of the same binary and configuration can disagree, and a few processes
switch state part-way through. No other kernel does this, and at the `l1` size and below only ordinary noise remains. Of
the 741 configurations, 32 have a median more than 5% above their minimum: 30 are `analytic` or `analytic_mix`, the
other two are 5.5% and 7.8%.

What it is not:

- **Address placement.** `aslr.txt`, 12 processes per configuration with and without address randomisation: `d4` is split 7
  fast and 5 slow with randomisation, 4 fast and 8 slow without it. `l4` is split in both as well.
- **Huge pages.** `thp.txt`, 10 processes per configuration with transparent huge pages on and with
  `prctl(PR_SET_THP_DISABLE)`: in both, `f64` is fast in all 20 runs, `l4` slow in 19 of 20, `fs` slow in all 20.
- **Clock frequency, or a busy hyperthread sibling.** `load.txt`, 45 processes sampled every 100 ms: CPU 0 averages 4.52 to
  4.69 GHz, with no difference between the states (for example `d4` at 3.25 ns and at 1.44 ns, both at 4.69 GHz), the hyperthread sibling is idle in
  both states, and the other CPUs are at most 0.29 of one CPU busy.

I did not establish the cause. The machine has no `perf`, so I have no counters. The states appear only in the kernel that
is limited by memory traffic and only once its data no longer fits in L1, and they cluster in time and depend on the
variant. Anything further would be a guess. The conclusions here do not depend on it: this kernel's lane and thread gains
exist inside L1, and above it no lane width was meaningfully faster than `f64` in either state.

### Does the vectoriser start from stores?

The earlier single-workload observation from `crates/occam-wasm/examples/perf.rs` was that summing `Lanes<2>` straight
into one scalar gave no `f64x2` arithmetic, and writing pairs to a buffer gave 88 such instructions. `examples/slp.rs`
tests it on two workloads and three targets, with a 1 to 4 width sweep and four ways to consume the lanes: `sum` (add
every lane to one `f64`), `store` (write the lanes to a buffer), `acc` (keep a `Lanes<W>` accumulator) and `bits` (XOR
the lanes' bits). Each timing is the median of 11 repetitions, with `black_box` on every call so the compiler cannot
merge calls. A few `v3` runs take 60 to 97 ms, below the protocol's 100 ms. The count is packed instructions from
`slp-asm.txt`, the time is ns per point from `slp.csv`, both at W=2.

| workload (target) | sum | store | acc | bits |
|---|---|---|---|---|
| bezier (wasm) | 131, 11.40 ns | 212, 6.55 ns | 0, 11.40 ns | 214, 5.75 ns |
| bezier (base) | 123, 7.34 ns | 202, 6.39 ns | 3, 10.56 ns | 390, 5.33 ns |
| bezier (v3) | 105, 7.95 ns | 195, 4.16 ns | 107, 7.33 ns | 959, 2.98 ns |
| cylinder (wasm) | 0, 3.95 ns | 0, 3.16 ns | 0, 3.85 ns | 69, 1.36 ns |
| cylinder (base) | 2, 3.10 ns | 0, 3.42 ns | 3, 3.10 ns | 118, 1.24 ns |
| cylinder (v3) | 2, 2.62 ns | 0, 2.78 ns | 4, 2.60 ns | 76, 0.72 ns |

**Measured:**

- Stores do help on the Bézier workload: `store` vectorises everywhere, and on wasm it is 1.7 times faster than `sum`.
- `sum` is not free of vector code there: 131 packed instructions on wasm, where the earlier workload had none. So "no vector
  arithmetic without a store" does not generalise.
- The cylinder at W=2 gets no packed arithmetic from `sum`, `store` or `acc` on any target, so a store is not sufficient
  either. This is the `analytic` W=2 trap again.
- `Lanes<1>` with `store` is loop-vectorised across points, at 1.35 ns on `base` for the cylinder, 2.5 times faster than
  `Lanes<2>` with `store`, so a one-lane loop can beat two lanes.

**Inference, not established:** the SLP vectoriser's seeds are stores and a few other patterns, and a strict `f64` sum is not
one it can reorder; integer XOR is associative, which may be why `bits` vectorises. The practical point does not depend on
this: whether a `Lanes<W>` kernel vectorises varies by kernel, width, target and consumer, so it has to be checked for each
kernel. It cannot be assumed from the shape of the code.

## Answer

**Nesting.** Threads across whole faces, lanes inside each task, as L28 says. Speed-ups multiply (5.2 to 5.5 from six
cores, times the lane gain) for every kernel whose time is arithmetic, up to 30.7 times over one scalar thread
(`bounds`, `Lanes<8>`, AVX2). The rule has three parts: each task owns its output columns outright, with no splitting
one column across threads below about 4 KiB per slot; claim whole faces in blocks; and keep the per-task data inside L1
for cheap per-point kernels, because above that their lane and thread gains shrink, and above the last-level cache the
threads give nothing (1.02 at six threads).

**Lane width per kernel class:**

| Class | Width | Measured |
|---|---|---|
| Masks and reductions (bounds, overlap tests) | 8 | 3.0 on `base`; 5.8 to 5.9 with AVX2 through `dispatch!`; on wasm 3.4 to 4.5 at W=4 to 16, no clear winner |
| Branch on every lane, written as masks (crossing number) | 8 | 2.6 on `base`; 3.9 to 4.7 AVX2; 3.3 to 3.8 on wasm |
| Grid-organised spline, no gather (Bézier) | 4 to 8 | 1.8 to 1.9 on `base`, 2.0 to 2.1 through `dispatch!`, 3.3 in a `v3` build |
| Grid-organised spline with span changes | 2 | 1.3 on `base`, 1.3 to 1.5 elsewhere |
| Spline with per-point spans (reference `bspline`) | 2, or none | 1.2 at most; reorganise around the grid first (`bspline_grid` is 1.5 times faster in plain `f64`) |
| Rational surface with derivatives | 1 or `fs` | 0.95 to 1.12 at W=2 to 8 once the gather is a loop (`gather.csv`); `fs` 1.10 |
| Analytic surfaces (data in L1) | 1, or AVX2 through `fs` | `f64` is loop-vectorised; `Lanes<2>` is a 2 to 3 times loss on every target; `fs` 1.46 at AVX2 |

**`Lanes<W>` or `fearless_simd`?** Plain `Lanes<W>` is enough for what it can reach, and it reaches only SSE2 in the
build `docs/DETERMINISM.md` allows. The gains that make this worth asking about (a factor of 1.5 to 2 over the SSE2
result, on the mask kernels) need AVX2, and under `forbid(unsafe_code)` the only way to get AVX2 here, short of a
`target-cpu` build that rule 5 forbids, is `dispatch!`. So
I would ask for it, for `dispatch!` over `Lanes<W>` rather than for explicit SIMD types: `d4` and `d8` gave most of the
speed-up with no kernel rewriting and the same bits. The explicit types are slower than plain lanes for `bounds`, and on
wasm plain lanes win for masks. The dependency does nothing for the reference spline workload.

Plain lanes need two habits. Gathers must be plain loops, because `array::from_fn` falling out of line cost the rational
kernel a factor of 2.3 at W=4. And each kernel needs its vectorisation checked, because a kernel can compile cleanly and
still run scalar, as `analytic` does at W=2.

## What this does not show

- One x86-64 machine with AVX2 and no AVX-512, and `wasmtime`, not a browser. No aarch64.
- The cause of the bimodal state. I only excluded address placement, huge pages, frequency and a busy sibling thread.
- The threaded runs use `std::thread::scope` and a mutex queue; which runner occam will use is `proving-ground.p11`.
- False sharing was sized for visibility, not for the protocol: the one-thread references take about 100 ms, but the
  six-thread runs at large chunks take 12 to 25 ms for `analytic`, below the protocol's 100 ms, and the chunks are not
  cache-line aligned.
- `fs` was measured at its native width only. Eight-lane explicit SIMD on AVX2 was not tried.
- `d4` and `d8` show what `dispatch!` buys. A hand-written `#[target_feature]` path was not compared: it needs `unsafe`.
- The kernels are simplified (fixed degree 3, tiny polygons in `crossing`). Trimming, and spans that vary inside a face,
  are not measured.
- Batching by kind (L29) is not settled here: `analytic_mix`, the branch-inside-the-loop form, was measured only at the size
  where the bimodal state hides any difference.
- `occam-math` is unchanged. Whether `Real::from_fn` should stop using `array::from_fn` is left to the crate's owner;
  only the spike's own gather was tested.

## What it decides

Decisions that belong to the user are in the next section. For the design:

- Evaluation is threads across faces with lanes inside each task, and whole faces are the unit of work.
- The lane width is chosen per kernel class (table above), and is a named constant per kernel, not one global width.
- `bspline`-style evaluation is reorganised around the grid before widening any lanes. Spans and gathers are what cost.
- Every `Lanes<W>` kernel gets a gate that checks it vectorised and how fast it runs on each target (L30). The
  `results/asm-*.txt` counts and `slp.csv` show what that check would have caught.
- Gathers in `Lanes<W>` code are loops, not `array::from_fn`.
- Output columns are sized and owned per task, and a batch is sized so that cheap per-point kernels stay inside L1.
- Beyond L3, cheap kernels are limited by memory bandwidth, so more threads and wider lanes buy nothing. The remedy there
  is fewer bytes per point, not more parallelism.

## Open questions for the user

1. **Add `fearless_simd` to the kernel, for `dispatch!` only?** Recommended: yes. Without it, `Lanes<W>` is confined to SSE2
   on x86-64 under `forbid(unsafe_code)`, and the mask kernels lose a factor of 1.5 to 2. Its price is a dependency, an
   `#[inline(always)]` chain and one copy of each kernel per level. Explicit SIMD types are not needed.
2. **Does `docs/DETERMINISM.md` rule 5 ("No `target-cpu`") stay as written?** No `v3` digest differed here, but the rule is
   the user's. If question 1 is answered yes, nothing needs to change, because `dispatch!` needs no `target-cpu`.
