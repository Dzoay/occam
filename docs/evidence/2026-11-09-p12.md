# `proving-ground.p12`: can the GPU generate display geometry?

In short: GPU write-through works, and the first release does not need it. A compute shader writing a `STORAGE | VERTEX` buffer, never read back, held 60 Hz at 4,000,000 points on a discrete GPU with 5.3 ms of GPU time and 0.2 ms of main-thread time. The CPU, re-evaluating the whole grid each frame, held 60 Hz at 399,424 points and fell to 30 Hz at 1,000,000, limited by `writeBuffer` on the main thread. But dragging one control point touches about 2% of the grid, and the CPU re-evaluating only that held 60 Hz at every size up to 4,000,000 points with under 5 ms of main-thread time. A static mesh costs the same to draw however its buffer was filled. Vertex pulling also held 60 Hz, at 4 to 5 times a stored draw's GPU cost every frame even when nothing changes. Independent evaluation disagrees along shared edges; evaluating each edge once removes that for almost no cost. Coordinates must be camera-relative. Large `writeBuffer` traffic lost the GPU device outright until it was bounded.

Code: `spikes/p12/` on branch `spike-p12`. Raw output is in `spikes/p12/results/`, each file headed by the command that made it.
`spikes/p12/run/sweep.sh` and `run/laptop.sh` hold those commands, and `run/tables.py` regenerates the tables.

## Question

The renderer draws on the GPU; that is decided. P9 found that GPU compute does not belong in `occam-mesh`: its results are 32-bit
and differ between adapters, and most of its cost is reading results back. P9 did not measure the case that avoids read-back: display-only
surface evaluation written straight into a vertex buffer, drawn and never read, in a page with a render loop. Does that earn a place in
the renderer, for what, and at what point counts? The full statement is in `spikes/p12/QUESTION.md`.

## What was measured

**Machines.** Timings not marked "laptop" ran on the measuring machine: an Intel Core i7-8700K, six physical cores (the browser pinned to
CPUs 0 to 5), governor `powersave`, whose only GPU is a discrete NVIDIA GeForce GTX 1080 Ti. Firefox 159.0.1 headless hides the adapter's name from the page; a compute cost
of under 1 ns per point is not a software renderer, so the page was on that GPU. **The machine was not idle**: an unrelated long-lived Firefox, seen in a process listing, was running at about 1% CPU, and other
investigations took the same lock between runs (never during one, though their file copies to the machine run outside the lock). The laptop is an Intel Core i7-1165G7 with integrated Iris Xe, Firefox
159.0.1, running other work at a load average near 6.7. **Laptop figures only compare adapters.** Chromium and WebGL2 were not measured.

**Build.** `rustc 1.99.0`, target `wasm32-unknown-unknown`, `RUSTFLAGS=-C target-feature=+simd128`, `lto = "fat"`, `codegen-units = 1`. No
hand-written lanes: the evaluator relies on the compiler's use of simd128.

**Workload.** P9's bicubic B-spline surface, 32 by 32 control points, positions and normals on an n by n grid, 32 bytes a point, drawn as
indexed triangles (`u32`, 6 (n-1)^2 indices) into a 1280 by 720 canvas with a depth buffer, in a `requestAnimationFrame` loop. One control
point (of 1,024) moves every frame.

**Candidates.**

- `cpu6`: six pool workers with separate wasm memories (P10's recommendation), simd128, `f64` inside and `f32` out, each returning a block of
  rows in a transferable buffer; the main thread calls `writeBuffer` per block. The evaluator tabulates the basis per grid line and combines
  control points per row (the ordinary tensor-product shortcut), which is faster than P9's general point-at-a-time evaluation.
- `comp`: a WGSL compute shader, a line-for-line `f32` translation, writes a `STORAGE | VERTEX` buffer; drawn in the same command encoder.
  Never mapped.
- `pull`: control points in a storage buffer, evaluated in the vertex shader from `vertex_index`. No compute pass and no stored vertices.
- `cpu6L` and `compL`: the same, re-evaluating only the rectangle of grid points the moved control point can affect (its four knot spans in each
  direction, about 2% of the grid). Vertex pulling cannot do this.
- `cpu4`: four workers, on the laptop only. A variant on the main thread (`cpu0`) appears only in the smoke run; it was dropped when the measuring machine's lock ran short.

**Measures.** Frame time is the gap between successive submits. *Edit to GPU done* runs from just before the control point changes (for the pool, before
the job is posted) to `onSubmittedWorkDone`. *Edit to next rAF* is that plus the wait for the next `requestAnimationFrame` after completion: an upper
estimate of when the frame can be on screen. A headless browser has no display, so true scan-out was not observable. Main-thread time sums the
synchronous segments on the page's thread. GPU busy times come from timestamp queries on the compute and render passes. Buffer memory is computed from what
was allocated: WebGPU has no memory query.

**Protocol.** Each configuration warms up for 30 frames and then records 180, or stops after 6 s with at least 7 (nothing-changing runs: 20 and 120, 4 s; verification runs: 10 and 30, 2 s); statistics are over those frames (minimum, median, 95th
percentile). The upload path changed during the sweep (see "Uploading large buffers lost the device"); `spikes/p12/web/render.html` as committed is the final version, and the CPU rows of the first table come from it. The frame is the repeat, so each configuration ran once; run-to-run variation was not measured. Output hashing does not apply: the
rendered output is pixels. Instead, for each candidate a control point was moved up and down and the canvas read back; the changed pixels and a reduced image are
compared across candidates. `rAF` in headless Firefox ran at 60 Hz, so frame times under about 16.7 ms cannot be seen as such: GPU busy time is the measure of headroom.

**Cracks and accuracy.** Read-back here is for testing only (`web/cracks.html`). Two patches share an edge, parameterised in opposite directions, and are
evaluated independently in the shader at equal and unequal densities along it; their edge positions are compared. Then the edge is evaluated once and both patches read it. The
accuracy test compares `f32` shader positions with `f64` positions computed in JavaScript, for the same part near the origin and far from it, with and without subtracting the
part's centre in `f64` before the `f32` control points are made.

### What the tables say

**Sustained frame time and the highest size that holds 60 Hz.** With the whole grid re-evaluated every frame, write-through and vertex pulling held 60 Hz at every size measured, up to 4,000,000 points (the sweep stopped there). The CPU pool held it at 399,424 points and not at 1,000,000 (33.3 ms), 1,999,396 (50.0 ms) or 4,000,000. The 200 ms at 4,000,000 points, measured over only 7 frames, is **probably partly an artefact**: that upload is split in two with a wait for the GPU after each piece, and two waits at the 100 ms polling floor described below would account for it, though I did not test that. What the CPU itself spends at that size is 28 ms in the slowest worker and 73 ms on the main thread.

**Where the CPU's time goes.** It is mostly `writeBuffer` on the main thread, about 0.5 to 0.6 ms per MB: 16.6 of 16.7 main-thread ms at 1,000,000 points, 72.7 of 72.9 at 4,000,000. Evaluation is not the limit, at 4.7 ms in the slowest worker at 1,000,000 points. The grid shortcut helps here: it comes to about 42 ns per point per worker at 4,000,000, against P9's 134 ns for the general per-point path on one wasm thread. Irregular points would not get that shortcut.

**Edit latency.** Edit to GPU completion was 17 to 19 ms for write-through and vertex pulling at every size from 99,856 points up, which is one frame: the work is done long before, and completion is reported at about the next frame. (At 10,000 points vertex pulling showed 2.7 ms, because completion is sometimes reported within the frame.) The CPU pool was 20 to 22 ms up to 399,424 points, 33.6 ms at 1,000,000, 80.8 ms at about 2,000,000 and 200.7 ms at 4,000,000. Adding the wait for the next `requestAnimationFrame` gives 33 ms for the GPU candidates at those sizes. **Local updates:** 20 to 21 ms for the CPU pool up to about 2,000,000 points, and 3 to 19 ms for write-through (18 to 19 from 1,000,000 points up). At this frame rate a local CPU update reaches the screen within about one frame of the GPU.

**Main-thread time.** Write-through and vertex pulling cost 0.1 to 0.2 ms a frame at every size. The CPU pool cost 1.8, 5.7, 7.3, 16.7, 33.0 and 72.9 ms over the six sizes; local updates 0.5 to 4.3 ms, again mostly `writeBuffer`, here one call per row of the rectangle.

**GPU busy time and static cost.** The compute shader costs about 0.9 ns per point on the discrete GPU, about the same as P9. With nothing changing, a stored draw costs 0.47 ms per 1,000,000 points whichever way the buffer was filled, and 1.76 to 1.91 ms at 4,000,000. Vertex pulling pays for evaluation every frame regardless: 2.31 ms at 1,000,000 points and 7.04 ms at 4,000,000 with nothing changing, and 7.08 ms under edits, against 5.28 ms for compute and draw together.

**Do the three agree on screen?** Moving the control point changed 605 or 606 pixels in every candidate, and the block-averaged 64 by 36 images of cpu6, comp and pull at 99,856 and 1,000,000 points are identical (largest difference 0 of 255, `results/verify.txt`). That is a coarse check: block averages hide sub-pixel differences.

**Run-to-run.** Each configuration ran once, with frames as the repeats. Medians and minima of frame time differ by more than 5% everywhere, because the frame gap is set by the 60 Hz tick and its jitter, which is why the p95 is the check used for 60 Hz. The CPU pool's main-thread figures changed between runs (at 99,856 points: 1.96 ms in the first run with one `writeBuffer` per block, 5.72 ms in the final run, which splits uploads into 2 MiB calls and flushes per block). The final run is what the table reports; part of that difference is the cost of the splitting and part may be load, and I did not separate them.

### Uploading large buffers lost the device

On the discrete GPU, large `writeBuffer` traffic lost the device with `Out of memory`, and the page could only report what it had so far. It happened during the 4,000,000-point write-through configuration, whose index upload was 96 MB in one call (`results/edit-comp-first-run-device-lost.txt`; the page did not yet record which step failed); with 32 MB a frame in six 5.3 MB calls at 1,000,000 points (`edit-cpu6-first-run-device-lost.txt`), whether two frames were in flight or one (`edit-cpu6-one-frame-in-flight.txt`); and with a 128 MB first fill at 4,000,000 points in 2 MiB calls without waiting (`static.txt`, `edit-cpu6L.txt`).

What made it stop, in the order tried: index data in 16 MiB calls; vertex data in calls of at most 2 MiB, flushed per block; and anything over 64 MiB in pieces with a wait for the GPU between them. Which of these were necessary was not separated. The integrated GPU did not lose the device at 1,000,000 points with 8 MB calls. **The cause was not established.** A limit on memory that is both CPU-visible and GPU-local would fit, but that was not tested. What it shows is that a CPU path of this size cannot simply call `writeBuffer` and hope. One frame in flight also halved the frame rate in this harness, because completion is reported about a frame late, so `edit-cpu6-one-frame-in-flight.txt` is not used for frame times.

### The polling floor

P9 saw about 200 ms per round trip in Firefox. Here, on the measuring machine (`results/poll.txt`, `poll-nocanvas.txt`, `idle.txt`), with a 16 MiB copy as the GPU
work, nine repeats each:

| Situation | Submit to `onSubmittedWorkDone`, median (min, max) ms |
|---|---|
| Nothing submitted for 600 ms, with a configured canvas | 100.5 (0.5, 100.8) |
| The same, before any canvas exists | 100.7 (77.4, 100.9) |
| Submitting every frame from `requestAnimationFrame`, 40 samples | 17.2 (1.7, 18.5) |

`mapAsync` after idle behaves the same (100.6 ms median). So the floor is about 100 ms per wait, and P9's 200 ms is consistent with two waits per round trip, though
that was not tested. **It does not survive in a loop that submits every frame**: completion is then reported within about a frame. **It does survive for an edit that
follows idleness.** Nothing submitted for 800 ms, then one edit and draw from `requestAnimationFrame`: edit to completion was 98 to 99 ms median for `comp` at 10,000 and at 1,000,000 points, `compL` and `pull`
(minimum 14.5 to 47.5 ms; nine repeats each). This is when JavaScript is *told*; whether the pixels reached the compositor sooner cannot be seen headless.
The laptop shows the same 100.9 ms idle floor (`results/laptop-edit.txt`).

### Cracks

Two bicubic patches, 16 by 16 control points, share an edge parameterised in opposite directions, the shared control points being one list reversed. Positions are
read back for this test only. One pixel is 2/1920 of a model unit, with the pair filling a 1920-pixel-wide viewport. Zoom multiplies the pixel figures. `results/cracks.txt`.

| Case | Samples along the edge | Positions that differ | Largest gap (model units) | Largest gap (pixels) |
|---|---|---|---|---|
| Independent, equal density | 501 and 501 | 481 of 501 (bit patterns) | 4.7e-7 | 0.00045 |
| Independent, unequal density | 501 and 317 | (different points) | 6.0e-6 | 0.0057 |
| Independent, very unequal density | 501 and 41 | (different points) | 3.7e-4 | 0.35 |
| Edge evaluated once, both sides read it | 501 | **0 of 501** | 0 | 0 |

Two facts matter. Evaluating the same curve independently from each side, even at equal density, gives different bits at 96% of the samples, because the two sides do
different arithmetic. The gaps are far below a pixel, but the rasterisation rule that stops holes between triangles relies on the triangles sharing identical vertex
positions, so any non-zero difference can show as pin-holes. Pin-holes were not counted; only position differences were. And with unequal densities the gap is a matter of tessellation, not rounding: 0.35 pixels at 501 against 41 samples, which zoom turns into a visible crack.

Evaluating the shared edge once and having both sides read that one buffer removes the difference completely. It costs almost nothing: 0.011 ms of GPU time for a 1,001-point edge pass, against 0.320 ms for a 1,001 by 1,001 patch, which itself was unchanged by reading the edge
(0.320 against 0.320 and 0.319 against 0.320, median of nine, timestamp queries). What it costs in design is more than that. A coarse patch whose boundary takes the edge's samples needs a stitching strip between that boundary and its first interior row. That was not built, so it is untested.

Near the origin the shader's `f32` is far below a pixel. A part 1,000 times its own size from the origin is 1.4 pixels off, and the error grows in proportion from there. **Camera-relative coordinates are needed**, and they

part of this test; a real renderer must build it relative to the same origin.

## Answer

**Write-through works, and it does not earn a place in the first release. The CPU mesh is good enough at realistic sizes.** P9's meshes of 1,002 and 10,001 faces had 454,558 and 1,850,878 triangles, so about 230,000 and 930,000 points, and a static mesh costs the same to draw whichever way its buffer was filled.

**For the use the brief calls the one that matters, a user dragging one control point, the GPU is not needed.** One control point of a bicubic surface reaches only its own four knot spans each way, about 2% of the grid here. The CPU re-evaluating just that rectangle held 60 Hz at every size measured, up to 4,000,000 points, with 4.9 ms of main-thread time at the largest.

**Write-through starts to pay only when a large surface changes as a whole, every frame, above somewhere between 400,000 and 1,000,000 points.** Re-evaluating the whole grid on the CPU held 60 Hz at 399,424 points and fell to 30 Hz at 1,000,000. The limit is not evaluation: at 1,000,000 points the slowest of six workers spends 4.7 ms. It is `writeBuffer` on the main thread, about 0.5 to 0.6 ms per MB, and the size of what can be queued at once. Compute write-through held 60 Hz at 4,000,000 points with about 5.3 ms of GPU time on the discrete GPU and 0.2 ms of main-thread time, and it never reads back, so P9's main cost is gone. What matters is how many points change per frame, not how large the model is: 399,424 changed points held 60 Hz on the CPU and 1,000,000 did not. Continuous change of a very large face with fixed topology (an animated deformation, a global drag) is the use write-through would serve. I know of no such feature in the first release; question 2 below asks.

**If it is ever added, it should be (b), compute write-through, and not (c), vertex pulling.** Vertex pulling needs no vertex storage, which saves 32 bytes a point. But it pays the evaluation every frame even when nothing changes, 4.0 to 4.9 times the GPU cost of a stored draw (7.04 against 1.76 ms at 4,000,000 points); under continuous edits it also cost more GPU time than compute plus a stored draw (7.1 against 5.3 ms). It cannot do local updates. On the integrated GPU it is already 7.3 ms a frame at 1,000,000 points.

**What the renderer's design needs from the start, so that this can be added without a rewrite:**

- **Vertex data in plain GPU buffers with a layout both a storage binding and a vertex fetch can read** (`vec4f` position and normal, 32 bytes a point, here), created with `VERTEX | STORAGE | COPY_DST`, and a draw call that does not care who filled the buffer. Static index buffers, separate from positions, stable across edits of unchanged topology.
- **Per-face ranges and dirty rectangles**, because local update is the cheap path whichever evaluator runs.
- **Uploads bounded per frame**: not more than about 64 MB at a time with a wait for the GPU in between, or a mapped staging ring. 128 MB at once lost the device with "Out of memory" on the discrete GPU. The cause was not established.
- **Shared edges as data of their own**, evaluated once and read by both faces, as P9's method does on the CPU, with stitching between an edge's samples and a coarser interior. This is what removes cracks, and it costs about nothing on the GPU.
- **Camera-relative coordinates from the first version**: an `f64` origin on the CPU, and only offsets from it, as `f32`, on the GPU.
- **A frame loop that keeps submitting during interaction.** After idleness, Firefox tells the page about a completed submission about 100 ms later. Do not gate input feedback on `onSubmittedWorkDone`.

**What must never depend on it (L23):** anything under the determinism contract. GPU results are 32-bit and differ between adapters. They must stay out of the kernel's digests and caches, `occam-mesh`'s output, picking and measurement against true geometry, exports, the watertightness check, and any test that compares bits. Display only, never read back outside a test.

## What this does not show

- **Nothing on a real display.** Headless Firefox has no scan-out, so "edit to next rAF" is an estimate of when a frame could be on screen, not a measurement of it. The 60 Hz `requestAnimationFrame` cap also hides any speed
  under 16.7 ms, which is why GPU busy time is reported.
- **One surface on a regular grid, one patch.** A real display mesh is thousands of small faces, not one 4-million-point dispatch, and per-face dispatch, bind-group and draw overheads were not measured. P9's batches averaged 1,300 to 2,800
  points. Faces are trimmed and irregular: the CPU evaluator's tabulated grid shortcut would not apply to scattered `(u, v)` points, where P9's general path (134 ms per million points on one wasm thread) is the relevant figure. The shader candidates do not use that shortcut.
- **One moving control point.** A feature edit that changes topology or many faces at once needs the CPU mesher anyway and was not measured.
- **The renderer on the main thread only.** Moving it to a worker with an `OffscreenCanvas` would take `writeBuffer` off the main thread but not reduce the upload itself; that was not measured.
- **The CPU at 4,000,000 points was measured over only 7 frames**, and its frame time includes polling waits between upload pieces. The idle-edit probe covers `comp`, `compL` and `pull` only: its CPU row was lost to the device loss.
- **No trims, no stitching.** GPU evaluation here covers an untrimmed rectangle. Faces with holes were not handled. The stitching strip the shared-edge method needs at unequal densities was not built.
- **The CPU pool ran at six workers only** on the measuring machine, so there is no speed-up curve here (P10 has one for wasm pools). Local updates write one `writeBuffer` call per row, which costs about 1.9 ms per MB against 0.5 to 0.6 for whole blocks; a tighter layout might lower it, and that was not tried.
- **Bicubic, non-rational only.** Other degrees and rational surfaces were not measured.
- **Firefox 159 on two GPUs only.** Chromium and WebGL2 were **not measured**, and neither was Safari. P9 reached only a software renderer in Chromium. Firefox hides adapter names; the limits that differ between the two adapters are listed above.
- **Each configuration ran once, with the frame as the repeat.** Run-to-run variation was not measured. The measuring machine was not idle (see above).
- **Buffer sizes are computed from what was allocated**, not reported by a driver. On the laptop the GPU shares system memory, which the memory cap may not see.
- **Pin-holes were not counted**, only position differences. The camera transform's own `f32` error was not part of the accuracy test.
- **The cited works were not re-read for this spike** (Piegl and Tiller, *The NURBS Book*, 2nd ed., 1997; the WebGPU and WGSL specifications). The book's edition and date were checked against a library record on 2026-11-09.

## What it decides

For the renderer: camera-relative coordinates from the first version; the contract in the Answer above, so that GPU generation can be added without a rewrite; and a render loop that keeps submitting during interaction. For L23: anything GPU-generated stays display-only, outside the determinism contract, the kernel's digests and caches, picking and measurement against true geometry, exports, and the watertightness check. For `occam-mesh`: nothing changes; it stays the authoritative mesh.

It does not decide the API: WebGPU or WebGL2 still waits on which browsers the first release must support, and WebGL2 was not measured here.

## Open questions for the user

1. **Which browsers must the first release support?** WebGPU is what makes any of this possible, and this spike measured only Firefox on two GPUs. The decision file already holds this question open.
2. **Is continuous whole-surface editing of very large faces a use the first release must serve?** I recommend no, and that the first release draws the CPU mesh with local updates. Write-through would then be added if a real workload asks for it.
