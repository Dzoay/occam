# Finding: `proving-ground.p11`, what runs the threads?

Code: `spikes/p11/` on the `spikes` line of work (branch `spike-p11`). Raw output is in `spikes/p11/results/`, the command
that produced each file is in its header, and `spikes/p11/run/tables.sh` regenerates every table below from those files.

## Question

Which candidate should run occam's threads: `std::thread::scope` with occam's own queue, or `rayon`, which would be a
dependency to ask the user about? The answer has to live with three constraints: the same bits at any thread count (L23),
threads composing with lanes (L28), and `#![forbid(unsafe_code)]` in the kernel's own crates, which limits what a
hand-written queue can do.

## What was measured

**Machine.** Intel Core i7-8700K, 6 physical cores (12 logical), governor `powersave`, single-core turbo above all-core
turbo, so speed-ups read a little low; this is stated and not corrected for. Threads are pinned to physical cores with
`taskset -c 0-<n-1>`. `rustc 1.99.0`, target `x86_64-unknown-linux-gnu`, `RUSTFLAGS` unset, the kernel's release profile
(`lto = "fat"`, `codegen-units = 1`, no `target-cpu`). `rayon 1.12.0` with `rayon-core 1.13.0`.

**Protocol.** Each speed-up configuration ran 9 times and each sweep, burst, idle and size configuration 7 times, cold
start 15 times, and the peak thread count, a count rather than a timing, 3 times. Tables give minimum and median, and rows
whose median is more than 5% above their minimum are listed and explained. Each serial workload takes at least 100 ms.
Output is hashed with `occam_math::Digest` after the clock stops. Every timing went through `spikes/tools/remote.sh`, one at
a time, on the measuring machine; `results/wasm.txt` is type checks and one run under `wasmtime`, with no timing, and ran
locally.

**A correction that matters to every baseline.** Every measured run, the serial loop included, happens on a spawned
thread. The first run did not, and the plain loop read 12% slower than the same work on a worker. The cause is glibc, not
the runners: the main arena trims its heap on `free`, so each repetition re-faults its output. On the bicubic workload the
loop takes 118 ms on the main thread, 104 ms on a spawned thread, and 101 ms on the main thread with trimming turned off
(`results/arena.txt`, `run/arena.sh`). Without the correction, speed-ups would read about 12% high.

**Candidates**, all behind one interface (`spikes/p11/src/exec.rs`), so that each workload is written once:

| Name | What it is |
|---|---|
| `scope-chunks` | Spawn-per-call `std::thread::scope`, one contiguous range per thread, decided before any work runs |
| `scope-claim` | Spawn-per-call `std::thread::scope`, threads claiming chunks from a shared atomic index |
| `pool` | A persistent pool over std primitives: a shared atomic index per job, no `unsafe`, `'static` jobs, the caller claiming work too, workers parking when idle |
| `pool-spin` | `pool` with workers spinning about 70 µs before parking (wake-up measurements only) |
| `steal` | Work stealing with no `unsafe`: one `Mutex<VecDeque>` per worker, boxed `'static` tasks, a real `join`, and ranges split lazily when stolen |
| `rayon-default` | `rayon`'s global pool. Under `taskset` its default thread count is the number of pinned cores |
| `rayon-fixed` | A `rayon::ThreadPool` built with `num_threads(n)` |

The interface takes `'static` closures because that is the only form all of them can implement in safe Rust; data reaches
a task through `Arc`. Every result comes back in index order, and there is no way to observe arrival order.

**Workloads.**

- `bicubic`: the reference even map. A bicubic B-spline surface over a 1600 by 1600 (u, v) grid, one row per task, by
  FindSpan, BasisFuns and SurfacePoint (Piegl and Tiller, *The NURBS Book*, 2nd ed., 1997, A2.1, A2.2, A3.5; the basis
  is that of Cox, *J. Inst. Maths Applics* 10, 1972, and de Boor, *J. Approx. Theory* 6, 1972).
- `uneven`: 5000 items costing 1 to 1000 units (about 1 µs each), by a hash the runner cannot predict, with hard items
  clustered in runs of 32 as hard pairs are in a boolean; one task per item. `uneven-auto` is the same work with the grain
  left to the runner.
- `nested`: 64 faces, then 8 to 64 curves within each face.
- `subdivide`: a bicubic Bézier patch subdivided by de Casteljau's algorithm (Farin, *Curves and Surfaces for CAGD*, 5th
  ed., 2002) under a tolerance that tightens towards one point, so the tree is deep there and shallow elsewhere. Runners
  with `join` fork down to depth 12. Runners without it expand 256 tasks serially and map a depth-first traversal over
  them (`subdivide`), or run one `map` per level (`subdivide-levels`).
- `pipeline`: broad phase, pair intersection, edge split, face split, classify, stitch; each phase a map with a
  deterministic merge, reading the merged output of the previous one.

**Probes with no runner.** `src/bin/freq_probe.rs` times fixed blocks of `spin` work on one thread after an idle gap, in
one pinned process or six independent ones, and reads `scaling_cur_freq` after each round. `src/bin/freq_barrier.rs` runs
plain threads that meet at a `std::sync::Barrier`, which is the shape of the wake-up test with no runner. They measure what
the cores do on their own, so that runner overhead can be separated from it.

**Scheduling references.** Work stealing: Blumofe and Leiserson, *J. ACM* 46(5), 1999, 720-748. The lock-free deque that
needs `unsafe`: Chase and Lev, SPAA 2005, 21-28. `steal` and rayon's adaptive splitter both use thief-splitting, rayon's name for splitting once per
thread and again when a job is stolen. A related adaptive scheme is lazy binary splitting: Tzannes, Caragea, Barua and
Vishkin, PPoPP 2010, 179-190. Helping while waiting for a stolen half: Wagner and Calder,
PPoPP 1993, 208-217. Hashing inputs: SplitMix (Steele, Lea and Flood, OOPSLA 2014, 453-472) and xorshift (Marsaglia, *J.
Stat. Software* 8(14), 2003). These citations were checked for existence and venue; the papers were not re-read for this
spike.

**The ceiling.** One core sustains 4.7 GHz and six cores at once 4.3 GHz (measured below), a ratio of 1.093, so no CPU-bound
parallel run on this machine can exceed 6 / 1.093 = 5.49× against a one-core baseline. The best medians (5.49 on `nested`) are at
that ceiling.

**Reading the table.**

- `pool` and `rayon` are equal on the kernel's plainest shapes, within 1% on `bicubic` (5.13 and 5.08), `uneven` (5.35 and
  5.37) and `pipeline` (5.25 and 5.23).
- Static partitioning is not enough: `scope-chunks` reaches 2.97× on `uneven` and 1.38× on `subdivide`, where the others
  reach at least 5.3× and 3.2×.
- `uneven-auto` leaves the grain to the runner. `pool` and `scope-claim` use a fixed chunk of `n / (threads × 8)`, 104
  items here, which can hold several runs of hard items, and get 4.09× and 4.01×. `rayon` and `steal` split adaptively and
  get 4.80× and 4.75× (best runs 5.30× and 5.10×). With one item per task `pool` gets 5.35×, so a runner without adaptive
  splitting needs the caller to choose a grain.
- `nested` is where `rayon` and `steal` win outright: 5.49× against 5.01× for `pool`, a 9.6% gap.
- `subdivide` is where forking looked necessary and is not. With the frontier expanded to 256 tasks, map-only runners get
  3.2× against 4.68× for `rayon`, `steal`. At the fork-join form's own granularity (depth 12, `subdivide-fine`) `pool` gets
  5.32× and `scope-claim` 5.28×, above the fork-based 4.68× to 4.78×. What the map-only runners lacked was grain, not
  `join`. Only `scope-claim` and `pool` were run on that form.
- `subdivide-levels`, one `map` per level of the tree, never exceeds 0.75×. It reads 0.46× of the serial loop even at one
  thread, so the cost is the breadth-first form and not the runner. Do not write recursion this way.
- `scope-chunks` reaches 4.02× on `pipeline`, whose phases have uneven item costs, against 5.1× or more for the others.

`tree` clones its executor per fork, a contended reference count for `RayonFixed` and `Steal` and free for the zero-sized
`RayonDefault`, and `RayonFixed::join` re-enters the pool through `install`. The same clones are part of `steal`'s 130 to 200
ns; how much was not separated. Forks this cheap only matter when work items are comparable in cost to a fork, and the
kernel's are not expected to be.

  per burst minus the gap is about 5.6 ms for `pool`, 5.8 to 5.9 ms for `rayon` and 6.1 ms for `scope-claim`, but 3.0 ms for

  performance state responding to recent activity differently depending on when cores go idle. That is an inference: it was
  not isolated.
- **For the kernel:** one short operation after a pause (a user clicking, say) runs at about 0.8 GHz on this machine

## Answer

**A small std-only pool is enough for the kernel-shaped work measured here, and `rayon` is not needed for speed.** The persistent pool
over std primitives (293 lines, no `unsafe`, `'static` closures) matches `rayon` within 1% at 6 threads on the reference map,
the 1000-fold uneven map with one item per task, and the six-phase pipeline. It sits within 7% of this machine's measured
ceiling of 5.49× on all three.

**`rayon` is genuinely better in four places**, by these margins:

| Where | `rayon` | `pool` |
|---|---|---|
| Nested faces and curves, 6 threads | 5.49× | 5.01× |
| Grain left to the runner on clustered costs (`uneven-auto`) | 4.80× | 4.09× (5.35× with one item per task) |
| Calls of 6 tasks of 100 µs | ×5.47 | ×4.98 |
| Items of 100 ns, one per task | 3.94× | 0.38× (5.23× with `Grain::Auto`) |

It also has a real `join` at 13 ns per fork and accepts closures that borrow, which a persistent pool cannot do in safe
Rust. It costs six crates, 100 KB and 2.6 s of clean build here, and it needs a target-specific branch on wasm for an explicit
pool.

**Forking is not required for recursion.** Expanding a frontier serially and mapping over it reaches 5.32× on `pool`, against
4.68× to 4.78× for fork-join at the same granularity (`subdivide-fine` against `subdivide`). What matters is having enough
tasks. With 256 tasks instead of depth-12 granularity, the same map-only form reaches 3.2×.

The other two candidates are out. `scope` per call costs 65 µs per call and oversubscribes when nested, although it borrows
freely and needs no pool. `steal` shows that work stealing is possible without `unsafe`, and it matches `rayon` on nesting and
on `uneven-auto` (5.49× and 4.75×). It pays for that with 130 to 200 ns per fork against 13, 27 µs per small call against 3.7
for `pool`, and 420 lines against 293. If those advantages are ever wanted, `rayon` is the better way to get them.

**Recommendation: build the execution layer's runner as the small std-only pool, behind the interface below, and do not ask
for `rayon` yet.** The reason is not to stay std-only for its own sake. On the plain maps the two differ by 1% or less, and the
one kernel shape measured where `rayon` is ahead is nesting, by about 10%. Adding a dependency for that is not yet justified by
a measured need. If a kernel workload turns out to hit one of the four rows above, or the `Arc` plumbing that `'static`
closures force becomes painful at call sites, the swap is an adapter of about 100 lines (`spikes/p11/src/rayon_exec.rs`) with no
change at any call site, because `'static` closures are also valid for `rayon`. That reverses cheaply; the other direction does
not, if call sites have learned to borrow. If the user would rather not own a small scheduler at all, that is a good reason to
take `rayon` now, and it is the user's call.

**The interface** every candidate implements in safe Rust, trimmed from `spikes/p11/src/exec.rs`:

```rust
pub enum Grain { Auto, Each, Fixed(usize) }

pub trait Exec: Clone + Send + Sync + 'static {
    fn threads(&self) -> usize;

    /// `f` over `0..n`, with the results in index order, whatever order they finished in.
    fn map<R, F>(&self, n: usize, grain: Grain, f: F) -> Vec<R>
    where
        R: Send + 'static,
        F: Fn(usize) -> R + Send + Sync + 'static;
}
```

Its properties are the point. Results come back in index order and arrival order cannot be observed. There is no `sum`,
`reduce` or `fold`, so nothing can depend on a split tree. `Grain` is explicit, and `Each` is safe for items above about 10 µs.
A panic in a task reaches the caller with its payload. A `Serial` implementation is the one-thread baseline and the wasm
fallback, and a target with no threads needs no separate call site. `join` is left out until a workload needs it; recursive
work expands a frontier.

## What this does not show

- That the kernel's real booleans match these stand-ins. `bicubic` and `subdivide` are real geometry; the costs in `uneven`,
  `nested` and `pipeline` are xorshift rounds.
- Anything off this one machine: six physical cores, Coffee Lake, x86-64, no hyperthreads used.
  The all-core and single-core clocks are what limit speed-up here. A different core count, or a laptop's thermal limit,
  will give different numbers.
- The ergonomic cost of `'static` closures at real call sites. The interface forced `'static` onto `rayon` too, so `rayon`
  with borrowed closures, as `par_iter` normally is used, was not measured and might be slightly faster.
- That the hand-written runners have no scheduling bugs. Every run in this spike finished with the right digest, but there is
  no model checking, and `pool` has the panic race noted above.
- Real threads on wasm, and how long a browser takes to start them (`proving-ground.p10`). `wasm32-unknown-unknown` was only
  type-checked.
- The 1 ms idle-gap regime. Above, at 10 ms or more, the slow-down is the frequency floor. At 1 ms, what distinguishes the
  runners was not isolated.
- A real comparison of work stealing as a scheduling policy at scale: `steal` is a simple `Mutex<VecDeque>` design, not a
  tuned one, and the machine has six cores.
- Threads and SIMD lanes together (L28; `proving-ground.p4`). A lane loop belongs inside `f`, and the interface does not get in
  its way, but it was not run.
- Peak memory, which was not measured at all.

## What it decides

If the user accepts the recommendation:

- The execution layer's first runner is a persistent pool over std primitives, with the caller claiming work too and helping
  while it waits, workers parking when idle, and work claimed in index order. It is rewritten test-first, as with everything
  on this branch.
- The interface is the ordered `map` above. Recursive work expands a frontier serially and maps over it, with a task count
  far above the thread count.
- Spawn-per-call `scope`, the no-`unsafe` work-stealing design, and reductions in the interface are out.

Whichever way O5 goes, the interface stands: it is what lets the choice change later.

## Open questions for the user

1. **O5, `rayon` in the kernel.** The evidence does not favour it decisively: the kernel's plain shapes are equal, and
   `rayon` is ahead by 10 to 17% on nesting, short calls and unchosen grain. Recommendation: not now, keep the swap open
   through the interface, and take it if a kernel workload needs it. Your rule against hand-writing merely to stay std-only
   applies here: if you would rather not own a small scheduler, or if borrowed closures matter more than one more crate
   family in the kernel, say so and the pool is never written.
