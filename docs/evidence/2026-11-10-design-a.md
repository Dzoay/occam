# Proposal A: columns first

A design for `proving-ground.design`, written to be attacked; it takes one side on purpose. Findings are cited by id and
lessons by L-number, each number with its source.

## 1. What this design optimises and what it gives up

It optimises the kernel for doing one thing to many items at once. The spikes put the time in bulk work of one kind:
sampling edges into parameter space is 61 to 67% of every analytic boolean (P1), surface evaluation is 45% of
tessellation (P9), and robust decisions are cheap only when a lane filter takes them in groups (P6). So entities live in
homogeneous columns: topology as struct-of-arrays inside copy-on-write chunks, geometry as one column per family and
degree. A chunk of 1,024 records is the unit of storage, of copy-on-write, of a parallel task and of lane batches. Batch
calls are the primary API; a per-item call is a view over the columns. Reports carry ids only, and a batched resolver
describes them. What it gives up is real. An edit in place costs more (S3-P3: 1.98 against 1.37 µs), and so does a
snapshot (314 against 47 µs). The one geometry store S4 built was 2.6 times slower than a plain enum on analytic
surfaces. And a report alone no longer says what an entity is:
the agent needs the resolver's output beside it, and a failed phase's scratch entities exist only while the failure is
in hand.

Changes from PLAN §4:

- **`occam-exec` is new, second.** Only the crate holding the execution layer may name `rayon` (the rayon decision),
  and keeping it out of `occam-math` leaves that crate with `fearless_simd` alone. `rayon` is native-only: an explicit
  pool returns "Not supported" on wasm (P11), and each browser worker runs `Serial` (P10). `Chunked<T>` lives here
  because a chunk is what a task is. Above `occam-math`, it lets the determinism stream run through `Exec`.
- **Intervals, rings, expansions and the batch filter go in `occam-math`:** numbers only, written once over `Real` (S2),
  where DETERMINISM.md rule 1 puts all computing. S2's predicates D1 to D5 are polynomials over `Ring` in `occam-geom`
  and `occam-intersect`.
- **The certified radius joins `Tolerance` in `occam-units`, as `Enclosed`.** S2 says it is a separate type on computed
  geometry, not a field of `Tolerance`; both are typed lengths.
- **Geometry codes go in `occam-report`'s closed catalogue.** A code is a name and wording, so the crate still depends on
  nothing of ours (L2, L4).
- **The resolver lives in `occam-topo`,** the lowest crate that sees topology, geometry and history (section 3g).

## 3. The seams

The sketches use the real names in `occam-report`, `occam-math` and `occam-units`; a comment marks each change to an
existing crate. Doc comments, `# Errors` sections included, are trimmed. A trait method ending in `;` is valid as
written; an inherent or free function ending in `;` gets an `unimplemented!()` body, under a test-only allow, when the
sketch is compiled. Types named but not shown are S4's (`Jet1`, `Jet2`, `Domain`, `Degeneracy`, `Closest`, `Analytic`,
`TriangleView`, `BatchKey`) or plain data defined then.

### 3a. Units and quantities

S1 found no dot, cross or norm in `occam-units`, so every formula dropped to `[f64; 3]`. S4 found that a derivative is not
three lengths, a unit axis is not a `Vector`, and a cone compared a length parameter with an angle tolerance. This design
types a parameter once per domain, so parameter columns stay plain `f64` for lane kernels.

```rust
// occam-units, frame.rs: CHANGED. The sealed `Role` gains `Rate`. A Tangent is length per unit of the parameter its

// and `component`.
#[derive(Clone, Copy, Debug, PartialEq)]

pub type Tangent<F, R = f64> = Triple<Rate, F, R>;

impl<F: Frame> Direction<F> {
```

### 3b. Maths and execution

`Real` gains comparison and selection, which S4 needed for degeneracies in lanes and P5 built through `to_array`, and the
two functions S5 says to own. Those make analytic batches pay: S4's lanes bought nothing because `sin_cos` ran one lane
at a time, while P9, computing `sin` and `cos` over `Real`, took a cylinder from 30.0 to 18.4 ns per point at width 2.

```rust
// occam-math, real.rs: CHANGED. The existing items stay; `from_fn` for `Lanes<W>` becomes a plain loop (P4).
pub trait Mask: Copy + Send + Sync + 'static { fn any(self) -> bool; fn all(self) -> bool; }

pub trait Real: sealed::Sealed + Copy + Debug + Send + Sync + 'static
    + Add<Output = Self> + Sub<Output = Self> + Mul<Output = Self> + Div<Output = Self> + Neg<Output = Self>
{
    type Mask: Mask; // bool, or LaneMask<W>
    // LANES, splat, from_fn, for_each_lane, abs and sqrt as today, then:
    fn lt(self, rhs: Self) -> Self::Mask; // exact; false where either is NaN
    fn le(self, rhs: Self) -> Self::Mask;
    /// The way to a minimum: `f64::min` stays banned, since its zero is unspecified (rule 2).
    fn select(mask: Self::Mask, yes: Self, no: Self) -> Self;
    /// Owned: the same bits on every target, width and build; about 0.75 and 1.5 ulp (S5).
    fn sin_cos(self) -> (Self, Self);
    fn atan2(self, x: Self) -> Self;
}

// level.rs: NEW. The only file that names fearless_simd (decision 2026-11-10). `run` and all it calls must be
// `#[inline(always)]` (P4). Every level gives the same bits, since nothing fuses: rule 5 stands.
pub struct Level(fearless_simd::Level);
pub trait Kernel { type Output; fn run(self) -> Self::Output; }
pub fn dispatch<K: Kernel>(level: Level, kernel: K) -> K::Output;

// interval.rs: NEW. `mid ± rad`, rounded outward by inflation, as Rust has no rounding modes (S2; Rump 1999).
#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Interval<R: Real = f64> { mid: R, rad: R }

/// Written over once: intervals in lanes for the filter, expansions (Shewchuk 1997) for the exact stage (S2).
pub trait Ring: Clone {
    fn add(&self, rhs: &Self) -> Self;
    fn mul(&self, rhs: &Self) -> Self; // and sub, neg
}
pub struct Expansion(Vec<f64>); // Ring for Interval<R> and for Expansion

pub enum Side { Below, Within, Above }
/// A computed value's enclosure can straddle the band's edge; then no decision is made (S2 item 3, O11).
pub enum Verdict { Decided(Side), Undecided }

pub trait Predicate: Sync { fn value<T: Ring>(&self, inputs: &[T]) -> Option<T>; }

/// Reported per operation: each 1% reaching the exact stage adds about 33 ns a decision (P6).
pub struct Decided { pub filtered: u64, pub exact: u64 }

/// One pass (P6): the filter in `Lanes<W>`, uncertified lanes recomputed in expansions inline, answers by item index.
/// `decide_enclosed` takes radii too and may answer `Undecided`.
pub fn decide<P: Predicate, const W: usize>(p: &P, columns: &[&[f64]], band: f64, out: &mut Vec<Side>) -> Decided;
```

The execution layer is P11's interface with `rayon` behind it, plus the chunked column. S3-P3 found the sequential merge
into one flat output was 6.9 of 14.6 ns per face at six threads. Here each task returns a whole output chunk and the
chunk list is the output column, so the merge moves pointers, and closures stay `'static` (the rayon decision).

```rust
// occam-exec: NEW.
pub enum Grain { Auto, Each, Fixed(NonZeroUsize) }

pub trait Exec: Clone + Send + Sync + 'static {
    fn threads(&self) -> usize;
    /// Results in index order, whatever order they finished in. No reductions (P11).
    fn map<R, F>(&self, n: usize, grain: Grain, f: F) -> Vec<R>
    where
        R: Send + 'static,
        F: Fn(usize) -> R + Send + Sync + 'static;
}

#[derive(Clone, Copy, Debug, Default)]
pub struct Serial; // the baseline, and the runner inside each browser worker (P10)

#[cfg(not(target_family = "wasm"))]
#[derive(Clone, Debug)]
pub struct Threads { pool: Arc<rayon::ThreadPool> }

pub const CHUNK: usize = 1024;

/// Copied on first write (S3-P3). The directory is a tree of fan-out 64: a snapshot clones one pointer per column, and a
/// first write copies one path, 64 pointers a level, and one chunk. Two levels hold 4,096 chunks, about four million
/// records, enough for the coedges of S3-P3's million-face model (4.16 a face); a third level is added past that.
#[derive(Clone, Debug)]
pub struct Chunked<T: Clone + Send + Sync + 'static> { len: usize, root: Arc<Vec<Arc<Vec<Arc<[T; CHUNK]>>>>> }

impl<T: Clone + Send + Sync + 'static> Chunked<T> {
    pub fn get(&self, index: usize) -> Option<&T>;
    pub fn set(&mut self, index: usize, value: T) -> Option<()>;
    pub fn from_chunks(len: usize, chunks: Vec<Arc<[T; CHUNK]>>) -> Self;
}

pub fn map_chunks<E, U, F>(exec: &E, len: usize, f: F) -> Chunked<U>
where
    E: Exec,
    U: Clone + Send + Sync + 'static,
    F: Fn(usize) -> Arc<[U; CHUNK]> + Send + Sync + 'static,
{
    Chunked::from_chunks(len, exec.map(len.div_ceil(CHUNK), Grain::Each, f))
}
```

### 3c. Geometry

S4's two layers stand, plus the layer S4 said must exist from the start: "families live in columns from the start,
because homogeneous data cannot be recovered from `dyn Surface` without a downcast." The object layer is a column
answering two batch shapes. **One surface, many parameters** is P1's sampling, P9's refinement waves and P12's dirty
rectangles. **Many surfaces of a family, one parameter each** is P6's predicate batches and bounds. S4's `Surface<F>`
stays for one surface at a time. Inside a family column the items are stored whole, in `Chunked` records of
`Family::Item` (a NURBS keeps its poles behind an `Arc`), not split into fields: the dominant batch reads one item at
many points, and P6's across-item batches gathered whole items into lanes. So `surface(item)` hands out S4's blanket
`&dyn Surface` view of a stored item.

S4's store, 2.6 times slower than the enum on analytic surfaces, re-sorted 5,000 queries and allocated on every pass,
and gathered frames through closures. This design forbids all three: batches arrive grouped (a face's samples lie on one
surface), outputs and scratch are the caller's, and frames are computed at construction (S4's cone). Whether that is
enough is the `geometry` milestone's first gate (section 8).

```rust
// occam-geom: NEW.
/// The canonical pair order depends on it (S4), so `occam`, which registers every family, tests it is unique.
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct FamilyTag(pub &'static str);

/// Nothing beyond the order asked for is computed (P8 item 1: 33 to 34% of whole-run time).
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Order { Point, First, Second }

/// Every defining number as canonical bits, in order, compared word by word on a hit (P8).
#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct ContentKey { family: FamilyTag, words: Box<[u64]> }

/// A lane width as a type (W1, W2, W4, W8): an associated const cannot be a const argument on stable Rust.
pub trait Width: Send + Sync + 'static { type Lanes: Real; }

/// Layer 1: one surface, written once over `Real` (S4). `eval_*` is total: undefined is NaN in that lane.
pub trait Parametric<F: Frame>: Sized + Send + Sync + 'static {
    fn eval_point<R: Real>(&self, uv: UvPoint<R>) -> Point<F, R>;
    fn eval_first<R: Real>(&self, uv: UvPoint<R>) -> Jet1<F, R>;
    fn eval_second<R: Real>(&self, uv: UvPoint<R>) -> Jet2<F, R>;
    fn domain(&self) -> Domain; // each ParamRange carries its ParamKind
    fn key(&self) -> ContentKey;
    fn degeneracies(&self) -> &[Degeneracy<F>];
    fn closest(&self, p: Point<F>, seed: Option<UvPoint>, tol: Tolerance, scratch: &mut Scratch)
        -> Result<Closest<F>, Report>;
    fn analytic(&self, _tol: Tolerance) -> Option<Analytic<F>> { None }
    fn triangles(&self) -> Option<&dyn TriangleView<F>> { None }
}

/// Layer 1b: a family's homogeneous column, with lane widths per kernel class (P4).
pub trait Family<F: Frame>: Send + Sync + 'static {
    const TAG: FamilyTag;
    type Item: Parametric<F>;
    type OnWidth: Width;     // one item at many points (P9: 2 for analytic surfaces with owned sin_cos)
    type AcrossWidth: Width; // many items at one point each
    fn batch_key(item: &Self::Item) -> BatchKey;
    /// The inverse of `key`: how a column absorbs another's items without a downcast.
    fn decode(key: &ContentKey) -> Result<Self::Item, Report>;
}

/// Layer 2: what everything outside a family calls. Dyn-compatible, and batch first.
pub trait SurfaceColumn<F: Frame>: Send + Sync {
    fn tag(&self) -> FamilyTag;
    /// Writes only the caller's columns that `order` asks for.
    fn eval_on(&self, item: u32, uv: &UvPoints, order: Order, out: &mut Jets<F>, scratch: &mut Scratch)
        -> Result<Defined, Report>;
    fn eval_across(&self, items: &[u32], uv: &UvPoints, order: Order, out: &mut Jets<F>, scratch: &mut Scratch)
        -> Result<Defined, Report>;
    /// Padded for rounding: a box too small is a silent wrong answer (S1, P8).
    fn bounds(&self, out: &mut Boxes<F>);
    /// A new version with `keys` appended, sharing the chunks it does not change.
    fn appended(&self, keys: &[ContentKey]) -> Result<Arc<dyn SurfaceColumn<F>>, Report>;
    fn surface(&self, item: u32) -> Option<&dyn Surface<F>>;
}

pub struct Jets<F: Frame> { pub p: Points<F>, pub du: Tangents<F>, pub dv: Tangents<F> /* , duu, duv, dvv */ }

/// One bit per item, found by a mask kernel: L6's per-item failure, which S4 reached only by scanning (its item 4).
pub struct Defined { bits: Vec<u64>, len: usize }

/// The caller's workspace, so no evaluation allocates (S4: the heap path cost 8.4 times the stack path).
pub struct Scratch { reals: Vec<f64>, indices: Vec<u32> }

#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord)]
pub struct GeomId { column: u16, item: u32 }

/// One column per family and batch key, created only through the registry `occam` fills.
#[derive(Clone)]
pub struct Geometry<F: Frame> { surfaces: Vec<Arc<dyn SurfaceColumn<F>>>, curves: Vec<Arc<dyn CurveColumn<F>>> }
```

Curves repeat the layers as `ParametricCurve<F>`, `CurveFamily<F>` and `CurveColumn<F>`, and parameter curves as a
column writing `UvPoints`. A sampled curve carries its achieved fit error in its content: without one, S1's refinement
broke 33 NURBS operations. `Analytic<F>` is S4's closed enum, grown to five surfaces and the line, circle and ellipse.

### 3d. Topology

O22 is fixed here: struct-of-arrays inside copy-on-write chunks, for S3-P3's read scaling (4.83 against 3.23 times at
six threads with no output, 2.42 against 1.86 with a reused output) and a walk of 2.48 against 3.55 ns. The directory
tree attacks the snapshot cost (section 1), unmeasured. The edit penalty is accepted: S3-P3 measured an edit as about a
microsecond of bookkeeping, and P1 found stitch at 0.3 to 0.6% of a real boolean.

Chunks hold 1,024 records. For struct-of-arrays, S3-P3 measured 100 scattered edits behind a snapshot at 22.8 µs an edit
with chunks of 1,024 against 29.7 with 4,096, and 2.0 against 7.1% more memory for the second version; the 1,024 figure
includes a flat-directory snapshot of 1,191 µs, which the directory tree should remove. A column chunk is 4 or 8
KiB, at or above the 4 KiB below which P4 saw writers false-share. The tables hold S1's list, each item backed by its removal.


Pinch vertices (S1 item 6) need no column: a vertex may have any number of edges, a loop may pass through it twice, and
the walk takes the next use by angle. The checker counts shells, the only check that notices a missing pinch (without
them S1's four exact Steinmetz cuts came back as one shell, and nothing else failed). The tolerance data is one
`Tolerance` per snapshot, `deviation` per edge, `radius` per vertex and a fit error per sampled curve. Nothing grows.

### 3e. Intersection

S4's ordered method list, in P5's order: closed forms (58 of 58 correct, within 1e-12), then the hybrid of subdivision
for start points and marching (104 of 110, 2 silent failures, against 13 silent for marching alone). Failure is part of
the result, because marching reported none of its 13 wrong answers.

```rust
// occam-intersect: NEW.
pub trait PairMethod<F: Frame>: Send + Sync {
    fn name(&self) -> &'static str;
    /// `None`: does not apply. A result may still say it is incomplete.
    fn attempt(&self, a: &dyn Surface<F>, b: &dyn Surface<F>, tol: Tolerance, budget: Budget) -> Option<Section<F>>;
}

pub struct Section<F: Frame> {

    pub unresolved: Vec<Report>,         // a stalled trace, a spent budget, an unresolved leaf (P5)

pub enum Contact<F: Frame> {

    /// A contact, or a loop smaller than `bound`: not a tangency (O24).

/// One result per pair, in pair order (L6), each pair in canonical order (S4). Threads across pairs, then a pair's
```

The boolean is P2's shape (a): pure phases, each an ordered map from frozen input to frozen output, with P2's data flow,
phase 3 as P2's three rounds around a frozen vertex table, and ids assigned only in merges. Each phase declares its
input's content key, unused for now: P8's advice to design for reuse now and build it later.

```rust
pub trait Phase: Send + Sync + 'static {
    type Input: Send + Sync + 'static;
    type Output: Send + Sync + 'static;
    const NAME: PhaseName;
    fn key(input: &Self::Input) -> ContentKey; // no run-specific ids (P8 item 4)
    /// Fails with every failing item in item order (P2), where S1 could report one.
    fn run<E: Exec>(exec: &E, input: Arc<Self::Input>) -> Result<Self::Output, PhaseFailure>;
    fn keep(frozen: &mut Frozen, output: Arc<Self::Output>);
}

/// Every phase output reached before a failure: what L5 asks a solver to hand back.
#[derive(Default)]
pub struct Frozen { /* prepared, candidates, sections, split, regions, labels: each Option<Arc<_>> */ }

/// The report holds ids only; `frozen` is what its scratch ids resolve against.
pub struct OpFailure { pub report: Report, pub frozen: Arc<Frozen> }

pub fn boolean<E: Exec>(exec: &E, model: &Snapshot, kind: BooleanKind, target: Id<Solid>, tool: Id<Solid>, step: u32)
    -> Result<Outcome<(Snapshot, Changes)>, OpFailure>
{
    let mut frozen = Frozen::default();
    let prepared = stage::<Prepare, _>(exec, prepare_input(model, target, tool), &mut frozen)?;
    let candidates = stage::<Broad, _>(exec, prepared.clone(), &mut frozen)?;
    let sections = stage::<Pairs, _>(exec, pairs_input(model, &candidates), &mut frozen)?;
    let split = stage::<SplitEdges, _>(exec, split_input(&prepared, &sections), &mut frozen)?;
    let regions = stage::<SplitFaces, _>(exec, split, &mut frozen)?;
    let labels = stage::<Classify, _>(exec, classify_input(model, &regions), &mut frozen)?;
    // The one sequential step: plans in region order, ids assigned in the merge, then the checker.
    let mut draft = model.draft(step);
    let sealed = draft.apply(stitch(kind, &regions, &labels)).and_then(|()| draft.seal(&Checker));
    let (next, changes) = sealed.map_err(|report| OpFailure { report, frozen: Arc::new(frozen) })?;
    Ok(Outcome::new((next, changes)))
}
```

The checker runs in `Draft::seal`, so no snapshot exists that it has not passed, in release builds too. It is batch
kernels over chunks: Euler characteristic and shell count, edges used twice in opposite directions, loop closure, edges
within their deviation of their faces, vertices within their radius of their curves, sheets consistent across seams. Its
failures are fault class `internal`. Filleting 20 edges gives a `Batch` of 20 outcomes (L6), and an edge whose radius is
too large carries `reduce-radius` with the largest feasible radius (L3), followed by test (L2).

## 4. Determinism

**Order** is item index everywhere. `Exec::map` returns results in index order and has no reductions (P11: `rayon`'s
float `sum` gave 7 bit patterns in 8 runs at six threads). Chunk boundaries are multiples of `CHUNK`, never set by the
thread count; a lane group is `W` consecutive items. A task grouping items by family for lanes (P6) partitions them
stably and writes back by index, and a group's remainder runs at width 1 with the same bits (`Real`'s contract). Pairs
are put in canonical order (S4). Plans apply in item order: P2 found this makes a boolean identical at every thread
count, where the shared-graph shape gave 4 raw digests at six threads.

**Ids** are assigned only in `Draft::apply`, in plan order, slots, generations and `GeomId`s alike, with free slots
reused in ascending order. A task never sees an id it created. Scratch ids index a frozen phase output in item order.

**Hashed:** a snapshot's digest is every column in slot order as canonical bits (rule 3). `gates determinism` extends to
the owned `sin_cos` and `atan2` (from a separate implementation, which S5 showed works), intervals, the filter,
expansions, `Exec::map` at 1 and N threads, and `dispatch` at each level; nightly, to corpus booleans and meshes at 1 and
N threads and on wasm. A future cache key holds every defining bit, both tolerances, an edge's range and the code
version, unrounded, and a hit is re-bound to the current run (P8: a rounded key lost a lens, and mixing identity by
pointer and by content cost 4.7 times the work).

**Kept out:** GPU results, 32-bit and different between adapters (P9, P12, the GPU-drawing decision); `f32` display
buffers; timings; thread count; dispatch level; arrival order; anything a pointer decides.

## 5. Parallelism

Threads across items, lanes inside each task, and the two multiply (P4: `bounds` at eight lanes with AVX2 reached 30.7
times one scalar thread). Tasks of 15 to 60 µs, 20 to 40 per thread (P6); `Grain::Each` above about 10 µs an item (P11);
a cheap kernel's data inside L1, since beyond the last-level cache six threads gave 1.02 times (P4).

| Phase or job | Unit of a task, grain `Each` unless stated | Lanes |
|---|---|---|
| Topology reads, broad phase, checker, `describe` | a chunk of 1,024 records | masks at 8 |
| Prepare (trims) and face split | a face; a large face by loop, since one face set P1's ceiling | one surface, many points |
| Robust decisions | 256 to 1,024 claimed dynamically, `Fixed(1024)` (P6) | interval filter at 4 |
| Sections | a pair; a hybrid pair's curves in fixed rounds (P5) | scalar |
| Edge split | three rounds: edges, pair events, clips (P2) | none |
| Classify | a region (P2: 5.4 times, against 3.9 with adaptive grain) | ray crossing at 8 |
| Stitch and apply | sequential | none |
| Mesh | edges, then a face per task (P9) | one surface, many points |
| Browser | 64 or more calls a job, `Serial` per worker (P10) | simd128 at 2 |

Lane width is chosen per kernel class, as a type (P4). Each lane kernel has a gate that checks it vectorised and beats
width 1 on each target, or it runs at width 1: P4 found kernels that compile cleanly and run scalar.

| Kernel class | Width | Evidence |
|---|---|---|
| Masks and reductions | 8 via `dispatch`; 4 on wasm | P4: 3.0 at baseline, 5.8 to 5.9 with AVX2 via `dispatch` |
| Interval filters | 4 | P6: 1.48 times; 8 added nothing without AVX2 |
| Owned `sin_cos`, `atan2` | 2; 4 via `dispatch` | S5: `sin_cos` 16.9 ns in std, 8.0 at 2 lanes, 4.3 at 4 in an AVX2 build |
| Analytic surface at many points | 2, gated | P9: cylinder 30.0 to 18.4 ns; P4's precomputed-trig kernel lost at 2 |

## 6. The open decisions

**O11, "cannot decide at this resolution" as a normal outcome. Assumed: yes.** It is `decide.undecided` with its failure
state; the pair fails, the phase collects every failing pair (P2), and the input is unchanged. A band decision at near
tangency snaps one vertex to the foot and stores `near_tangent_shift` as its radius: S2's `b-interval-snap`, which on
16-step adversarial chains failed 44% and was wrong against nominal in 8%, never against its own numbers. *If no:*
`Verdict` loses `Undecided`, `decide_enclosed` must pick a side, and S2's only measured ways to always pick were wrong
against nominal in 25 to 44% of chain steps. `occam-ops` then needs a policy for what an always-returns kernel returns.

**O12, the default `eps`. Proposed: 1e-7 mm and 1e-9 rad, per model, with a warning when the band is below 1e-11 of the
model's extent.**
- S1's answers did not change from 1e-5 to 1e-9 mm, bar 2 reports where an offset equalled the tolerance.
- Smaller costs. S1's `open` flags rose from 3 at 1e-7 to 9 at 1e-8 and 14 at 1e-9. At 1e-9 S2's intervals failed 11.1%
  inside the band and 35.2% at exact tangency, against 0.2% and 5.2% at 1e-7, likely because the band nears what
  intervals resolve at a scale of 8,192.
- Larger costs too. A band decision moves a vertex `sqrt(2 R eps)` (S2): 1.1e-3 mm at 1e-7 with R of 6 mm, 3.5e-3 mm at
  1e-6, and the band hides features thinner than itself (S1 item 11).
- The evidence is densest at 1e-7 (S1, S2, P6), and P6 found every corpus near-tangent decision certified there.
- 1e-9 rad is S1's value, matching 1e-7 mm on a 100 mm lever, the size of S1's models.

The warning threshold is a guess: S2 did not split its 1e-9 failures by scale, and at scale 8,192 its band was 1.2e-11 of
the scale at 1e-7 (fine overall) and 1.2e-13 at 1e-9 (failing). *If the user picks another value:* only the default and
the warning change; band-edge tests are written relative to `eps`.

**O14, owning `sin_cos` and `atan2`. Assumed: own them.** Without them analytic batches run one lane at a time, which is
why S4's lanes bought nothing. *If no:* analytic families run at `W1`, std's functions are allowed scalar through
`occam-math`, and their bits differ between native and wasm on 1 to 12% of calls (S5).

**O16, the browser and server promise. Assumed: identity for owned functions only, no promise of the feature.** *If
promised now:* the nightly run compares wasm and native corpus booleans, and every new transcendental is owned first.

**O18, requirements on the hosting page. Assumed: none.** P10's pool needs no COOP or COEP; threads gained 2 to 14% warm
and nothing cold. *If required:* the kernel does not change, but shared-memory threads still need nightly and
`-Zbuild-std` (O10), so the facade would carry two builds.

**O21, an exact third derivative. Assumed: two orders, differencing above.** The bracket test's constant-radius fillet
needs an offset's first derivative, the base's second. *If a named feature needs a third:* `Order` gains `Third`, `Jets`
four columns, and `Parametric` an `eval_third` defaulting to differencing `eval_second`, so every family compiles at S4's
differenced accuracy (about 1e-5 at second order for its offset) until it overrides it.

**O22, the layout inside chunks. Fixed: struct-of-arrays.** *If array-of-structs:* tables become `Chunked<FaceRecord>`
and the like, views read fields, and batch kernels gather from strided records: read scaling of 3.23 against 4.83 times,
for snapshots of 47 against 314 µs and edits of 1.37 against 1.98 µs (S3-P3).

**O23, narrowing L29. Proposed wording:** "Group geometry by family and degree, always: for memory (15% less, S3-P3), for
one dispatch per batch (sorting by kind 14 to 18%, S4; batching 1.8 to 3.3 times on analytic surfaces and 1.2 to 1.4 on
NURBS, P9), and for lanes only where a gate measures a gain (P4). Marching stays scalar, parallel across curves (P5)."
It keeps a speed claim S3-P3 proposed to drop, because P9 measured it with `sin` and `cos` over `Real`, which S3-P3
lacked. *If S3-P3's wording is recorded:* geometry still lives in columns (S4's reason), analytic families run at `W1`,
and lanes stay for NURBS by degree on wide-vector targets.

**O24, a loop below the resolvable size. Assumed: a reported result,** `Contact::BelowResolution`, with the section
marked incomplete. The boolean treats a bound inside the band as touching, the band's meaning, and one above it as
`decide.undecided` with `below-resolution`. *If a contact point is preferred:* the variant goes, and P5's 2 silent
failures stay silent.

**O25, coincident surfaces. Proposed: no follow-up spike; a named step in `booleans`, test-first from S1's 32 reports and
S6's c01 to c03.** They are S1's largest failure class, and the bracket test makes them likely: a hole cut "through" a
plate by a tool exactly the plate's height makes coplanar faces. S6's agents fixed all three by inflating the tool, which
changes the user's geometry. The analytic presentation detects both kinds exactly, so `Coincidence` is in the result
from the start, and until the step lands `boolean.coincident-surfaces` carries `move-apart`, followed by test. *If a
spike comes first:* the step waits, and coincidence stays a reported failure.

**O26, what `Report` carries. Fixed: ids only.** Section 3g gives where the resolver lives (`occam-topo`), who calls it
(`occam`, on every result) and how the description reaches the CLI's JSON (the envelope's `resolved` map). *If geometry
goes in the report:* `occam-report` gains `Description` as plain data, `resolved` goes, and each failure site fills its
own, one at a time instead of in one batch.

## 8. What this design is least sure of

**That a geometry column can match the enum on analytic surfaces.** I blame S4's 2.6 times on its re-sorting, allocation
and closures, but S4 did not break the cost down. *Shown wrong by:* the `geometry` gate. Geometry would still be stored
in columns, but analytic evaluation would go per item, and column batches would serve only NURBS and predicates.

**That the directory tree removes struct-of-arrays' snapshot cost.** S3-P3 measured flat directories only: 314 µs at
chunks of 4,096 and 1,191 µs at 1,024. *Shown wrong by:* the `maths` benchmark. If a snapshot plus one scattered edit at
10^6 faces costs over about twice array-of-structs' 92 µs, chunks go back to 4,096, and O22 deserves another look.

**That lanes earn their machinery on the build occam ships.** S3-P3 established no lane gain on baseline x86-64, P5 found
under 3% in intersection, and P9 found wasm simd128 lanes mostly no faster than scalar; most of the case for columns is
avoided work and one dispatch per batch. *Shown wrong by:* the vectorisation gate setting most kernels to width 1. The
columns stay for memory and scaling, and the `Width` types become dead weight.

**That ids-only reports serve an agent as well as enriched ones.** S6's blind control put enriched fields inside the
report (6 of 6 handled, against 4 of 6). The envelope carries the same information beside it, a shape no agent has
tried, and scratch ids die with the call. *Shown wrong by:* the blind control rerun doing worse than S6's enriched run.

**That bulk work stays where the time goes.** P1's 61 to 67% is S1's sampling at a fixed density, discarding derivatives,
so much of it is a choice (P8). With that fixed, P8 found face split, trims and classification remain, and P1 found one
large face sets the ceiling. *Shown wrong by:* a profile of the first real boolean dominated by single-entity traversal
and the sequential apply. Then the edit penalty outweighs the read scaling, and O22 should be revisited.

**How often real models reach the band edge.** P6 found the corpus never does, and that 2.8% of decisions on the exact
path took 75% of the time. *Shown wrong by:* an exact-path share above about 1% in the first booleans on the NIST parts.
The exact stage would then need an arena (P6), and grouping by family inside a task may not keep lanes full.
