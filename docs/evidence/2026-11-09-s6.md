# S6: can an agent repair a model from the reports alone?

Plan step `proving-ground.s6` ([the milestone](../plan/proving-ground.md)). The code is throwaway, on branch `spike-s6`, in
`spikes/s6/`. Nothing here is copied into a crate (L51). Raw logs, each agent's answer and the commands are in
`spikes/s6/results/`.

**Sample size: ten cases, each run once, by one model (Haiku), 23 agent runs in all. This is a rough indication and no more.** A
fraction of 9 of 10 cannot be told from 8 or 10 of 10, and no repeat runs measure how much the same agent varies.

## Question

Given a failing boolean, its JSON report and a command-line driver that lets it change inputs, can an agent that reads no source
code repair the model? It is a goal, not a gate. It answers what `Report` is missing (L1, L2, L5).

## What was measured

**The driver** (`spikes/s6/src/bin/driver.rs`) is built over a copy of the S1 prototype. It takes a case as JSON (the corpus
format, plus a tolerance), runs it and prints the outcome as JSON. Every call appends to a log and a sixth call in one case
directory is refused, so the attempt count and each input tried come from the tool, not from the agent's account of itself. S1's
limits carry over: no coincident surfaces, no cones, tori or fillets, no NURBS against anything but a plane, and a single
thread.

**The cases** (`spikes/s6/cases/`, fixed before any run, with `ACCEPTANCE.md`). Ten, covering each failure kind S1 reports:

| case | what it is | failure kind |
|---|---|---|
| c01 | two boxes sharing four side planes | `coincident-surfaces` |
| c02 | a box resting on a box | `coincident-surfaces` |
| c03 | coaxial equal cylinders | `coincident-surfaces` |
| c04 | crossed cylinders offset by about the tolerance | `dangling-section` |
| c05 | a NURBS block cut just below its peak | `dangling-section` |
| c07 | coaxial stepped cylinders, with S1's `S1_NO_HINT` removal switched on to stand in for a kernel bug | `loop-not-closed` |
| c08 | a NURBS block cut by a sphere | `unsupported` |
| c09 | the common of two boxes that do not touch (infeasible) | silent empty result |
| c10 | a tolerance of zero | `tolerance-out-of-range` |
| c12 | a hole of radius zero (infeasible input) | `hit-not-on-curve`, `gap` infinite |

**The protocol.** One fresh Haiku agent per case, one at a time, with at most five driver calls. Its brief held the request, the
failing input, the failing report and how to call the driver, and nothing else; it was forbidden from reading any source file.
The acceptance rule for each case was written before any run. *Repaired* is a passing result in the driver's log. *Correctly
declined* is for the cases marked so: the agent stops, does not claim success and names the real reason.

**Enrichment** (`spikes/s6/src/enrich.rs`, switched by `S6_ENRICH`). After the baseline, the reports were extended with what the
baseline agents said they lacked, and the failure was run again.

**The blind control, added after the baseline.** The baseline agents mostly solved the cases by reading the input's numbers,
not the report, so the baseline says little about whether the report is enough. Six cases were therefore run with every number in
the request withheld, once with S1's reports and once enriched, so that what the agent knows about the geometry can only have
come from a report. The agent sends relative edits (`spikes/s6/blind.py`). The same acceptance rules apply.

**Limits of the setup.** The ban on reading source is on the honour system: each agent was told, and each reported that it had
read nothing it should not, but only the driver's attempt log is objective. The baseline briefs showed the corpus case id, which
for c05, c08, c09 and c12 hints at the problem (`nurbs-near-peak`, `nurbs-vs-sphere`, `disjoint-common`, `zero-radius`); the
input numbers said the same thing, but the blind control masks the id. The brief told the agents a `nurbs_block` could be moved,
which is wrong and cost c08 one attempt.

## Results

### Baseline: S1's reports as they are, input numbers visible, ten cases

| case | attempts | outcome | what the agent did |
|---|---|---|---|
| c01 coincident, four shared planes | 1 | repaired | grew the tool box 1e-5 mm in x and y; volume unchanged to rounding |
| c02 coincident, box on box | 1 | repaired | overlapped the boxes by 0.01 mm |
| c03 coincident cylinders | 1 | repaired | tool radius +1e-4 mm |
| c04 dangling, offset near tolerance | 1 | repaired | set the 1.1e-8 mm axis offset to zero; volume within 3e-8 of the reference |
| c05 dangling, NURBS near peak | 2 | repaired | moved the tool down 0.5 mm, then 0.2 mm |
| c07 loop-not-closed, simulated kernel bug | 5 | **miss** | five input changes, all failing the same way; it stopped, but could not say whether the fault was its inputs or the kernel |
| c08 NURBS against a sphere | 3 | correctly declined | named the unsupported surface pair after trying tolerance and rotation |
| c09 common of disjoint boxes | 2 | correctly declined | the boxes do not touch; it ran two control cases to confirm the operation was sound |
| c10 tolerance zero | 1 | repaired | set the tolerance to the default |
| c12 radius zero | 1 | repaired | said the zero radius was the cause and that the value 1 mm was its own choice |

**Handled: 9 of 10** (7 repaired, 2 correctly declined). The one miss is c07. Under the acceptance rule fixed in advance it needed
the agent to name a fault the inputs cannot fix; the agent said it could not tell.

Five of the seven repairs (c01, c02, c03, c04, c12) came from reading the input's numbers. In c12 the report pointed the wrong way,
at a section that misses its curve by an infinite distance, and the agent found the zero radius in the input instead. c05 came from
the failure's code, the user's stated intent and two tries. Only c10's message named the problem outright. Seven of the ten agents
asked unprompted what a reported entity was (its operand, surface or position), and four of them said the id made no sense to them
(`4294967298` is a side and a face index packed into one integer, which nothing explains).

So 9 of 10 says the task can be done with the input visible. It says little about the reports, and that is why the control below
was added.

### The enriched report on the one failure, input numbers still visible

c07 again: five attempts, all failing. The agent now concluded that the failure "looks like a kernel defect in the face-split step",
citing the `fault` field, so it passes the rule: **10 of 10 handled, with the enrichment**. Two caveats. The fraction moved on one
case. And the attempts did not fall: `fault_detail` said that small changes "may move the failure", which invited them. The
agent also read "does not show that the input is at fault" as "says the input is not at fault", which is stronger than what was written.

### Blind control: every number in the request withheld, six cases, added after the baseline

The agent sees the operations with `"?"` for every number and can send only relative edits, so what it knows about the geometry can
come only from a report.

| case | S1's reports | enriched reports |
|---|---|---|
| c01 coincident | 3 attempts, repaired by inflating the tool in decreasing steps | 1 attempt, repaired: inflated once, by the listed `min_separation`, because the report named all four pairs |
| c04 dangling | 1 attempt, repaired by loosening the tolerance, believing it was the default 1e-7 mm. It was 1e-8 mm | 1 attempt, repaired: followed `change-tolerance`, knowing the value in force |
| c05 dangling | 4 attempts, repaired (tool moved 0.03 mm) | 4 attempts, repaired (0.01 mm). Understood that the plane is 75 nm below the peak, but lost two attempts to my `change-tolerance` remedy, which cannot work here |
| c08 unsupported | 3 attempts, **miss**: declined for an invented cause ("a closed cavity is not supported") | 0 attempts, correctly declined: named the unsupported surface pair |
| c09 silent empty | 4 attempts, correctly declined: found the 10 mm gap by inflating until something touched | 3 attempts, moved the tool and said so, which the rule passes. Told the separation, it changed the user's geometry rather than decline |
| c12 zero radius | 3 attempts, **miss**: "repaired" by inflating the radius 0.0001 mm. The operation succeeds, closed, Euler 0 (genus 1), with a hole no one wanted and a true radius of zero that the report never named | 2 attempts, repaired: named the invalid parameter, chose a radius and said so |
| **handled** | **4 of 6**, 18 attempts | **6 of 6**, 11 attempts |

In c12 the enriched run's first attempt, radius 5, hit a new code, `classify-inconsistent` (a hole tangent to all four sides of a
10 mm square, a valid input). The driver labelled it `internal`, and the agent said it needed to know whether that was a tangency or
a kernel fault. A fault class has to come from the failure's cause, not from a default for its code.

## Answer

**Yes, on this small sample, but the input numbers carry most of it.** With the input visible, 9 of 10 failures were handled on
S1's reports as they stand (7 repaired, 2 correctly declined), and 10 of 10 once the reports were enriched and the one miss rerun.
With the numbers withheld, so that only the reports could inform the agent, 4 of 6 were handled, and 6 of 6 with enrichment; attempts
fell from 18 to 11. **All of these are from ten cases and one model, run once each, and the blind control was added after the
baseline: a rough indication and no more.** The sharpest single result is a wrong success: blind, on S1's report, one agent reported
that it had repaired a zero-radius hole by setting a radius of 0.0001 mm, with every check passing.

**What `Report` is missing.** Counted over the ten baseline agents unless stated. Where the blind control tested a field, that is
stronger evidence than an agent asking for it.

| what | where it goes | evidence |
|---|---|---|
| **What an entity is, in the caller's terms:** the operation and operand it came from, its surface type with parameters, its extent | `EntityRef`, or a `Report` field beside it | 7 of 10 asked; 4 said the id was unreadable. Blind c08, without it, declined for a cause it invented; with it, 0 attempts and the right reason. Blind c01 went from 3 attempts to 1 |
| **The tolerance in force** and what was compared with it | `values`, whenever a tolerance decided the outcome | 4 of 10 asked. Blind c04 reasoned from the wrong tolerance |
| **A fault class per occurrence:** invalid input, not implemented, numerically sensitive, internal | a catalogue field, chosen per failure | c07: "I could not tell a repairable input from an unsupported one", a miss, then handled with it. Blind c08. Blind c12 shows a default per code misleads |
| **Text, or closed reason codes** | `NamedValue` text variant, or a reason enum | `reason` was the length of a message: c08 asked what "ratio 37.0" measures, in both runs |
| **An invalid input is its own code,** naming the operation, parameter, value and rule, found before any geometry | new catalogue code and a validation step | c12. Blind on S1's report: a false repair. Blind enriched: named at once |
| **An empty result is a diagnostic,** with reason and separation | new code on `Outcome.diagnostics`, which exists | c09 asked. Blind on S1's report it took 4 probes to find what the report could have said. c05, tolerance 1e-3: `ok`, volume 0 |
| **Remedies, populated and tested** | `remedies`, held to L2 | 6 of 10 said the empty list left them guessing. Followed in blind c01 and c04, 1 attempt each. A wrong one cost blind c05 two attempts, which is exactly what L2 is for |
| **Where it failed and how close to tangency:** the dangling end's position, the distance between axes against the radii, the plane's clearance from the extreme | `partial.values` (L5) | c04 and c05 asked; blind c05 understood a 75 nm sliver from it. It did not reduce the attempts in that case |
| The phase by name, not number | catalogue | c01 asked. Small |

**Not shown to be needed.** The list of every failing pair: blind c01 used it, but blind c09 ignored it and spent two attempts because
of it. `last_valid`: a placeholder that no agent used. **Already good:** the `code` tells an agent what kind of problem it has, and the
`partial` counts (`section_curves`, `regions`) were used by at least four agents to work out where the failure happened.

**What it does not say.** The enriched fields were computed by the driver from the operands and were spliced into the report's
JSON. They are a test of the information, not of a type. Their numbers (a minimum separation of ten tolerances, a suggested move of twice
the gap) were guesses made for these cases.

## What this does not show

- **Anything statistical.** Ten cases, one run each, one model. The blind control is six cases, and it was added after the baseline
  had been seen. A difference of one or two cases between runs is within what one agent's next run might do differently.
- **That a kernel's reports are enough for a real user's model.** The cases are small, from S1's corpus or written for this
  spike, and each has a single boolean. A real failure deep in a history, or one whose cause lies far from the reported face, is
  harder, and is untested.
- **That the prototype's own failures are representative.** The kernel here is S1's: it reports three kinds of failure in its
  final state, and the fourth, `loop-not-closed`, exists only because a switch deliberately removes a piece of data. Which report
  fields a future kernel's failures need may differ.
- **That the enriched fields are the right design.** They are what the driver could compute cheaply, chosen from what agents
  asked for. `near_tangency` and the suggested distances were written for these cases. No enriched field was tested as a
  `Report` type, or round-tripped through the schema. And the `fault` wording that the enriched c07 run was graded on was written after the
  baseline run had shown what the grader would be looking for.
- **That the agents obeyed the ban on reading source.** Every agent said it read nothing forbidden, but the only objective record
  is the driver's log, which sees calls and not file reads.
- **That Haiku is a fair proxy for an agent driving occam.** A stronger model might do more from less, and would also spend more.
- **Whether remedies are safe to follow.** Nothing here follows a remedy mechanically. L2's test, that following a remedy
  succeeds, was not run on the enriched remedies.

## What it decides

Nothing is decided here. It is evidence for `proving-ground.design` and for `bedrock.report`'s catalogue. It supports these inputs:

- Add to `Report`, or to the catalogue, the fields listed in the Answer. The two that the measurements bear on most strongly are an
  entity's description in the caller's terms and a fault class.
- Give `NamedValue` a way to carry text, or replace free-form reasons with a closed set of reason codes. S1 could not say why it
  stopped: `reason` was the length of a message, and the agents read it as a ratio of something.
- Validate inputs before any geometry, and give each kind of invalid input a code of its own.
- Report an empty result as a diagnostic on the `Outcome`, which already has somewhere to put one.

## Open questions for the user

None needs an answer before this finding can be used. One is worth a decision at `proving-ground.design`: whether `Report` carries
geometry (a surface's type and parameters, and a position) or only ids that a caller resolves through a separate query. The
blind control says an agent needs that information; it does not say which of the two is the better way to supply it.
